Apiserver 請求流程與 Admission

整理於 2026-10-23 · 起因:WAS PodGroup preemptionPolicy 的 upstream bug(kubernetes#143252)· 相關筆記:Kubernetes WAS Overview(第 9 節)、Priority and Preemption、Operator RBAC、Gang Scheduling Mechanics

重點:對 kube-apiserver 的寫入請求(create / update / delete),不管來自 operator、kubectl 還是 controller-manager,在存進 etcd 之前都要經過一連串關卡。admission controller 是其中一段,能修改物件或直接拒絕請求。

  • 讀取請求(get / list / watch)不經過 admission。
  • WAS 的 bug 就發生在 operator 送出 Create(PodGroup) 的這一趟:API defaulting 先補了值,Priority admission 再拒絕,PodGroup 根本進不了 etcd。

1. 一個寫入請求在 apiserver 裡的順序

  1. Authentication

    確認是誰發的,例如 KubeRay operator 的 ServiceAccount。

    失敗
    401 Unauthorized

  2. Authorization(RBAC)

    確認這個身分能不能對這個資源做這個動作,例如 create podgroups。

    失敗
    403 Forbidden;見 Operator RBAC

  3. Decode + API defaulting

    把 request body 轉成內部物件時,跑該型別的 SetDefaults_*,把沒填的欄位補上預設值。

    WAS bug 起點
    SetDefaults_PodGroup 把 nil 的 preemptionPolicy 補成 PreemptLowerPriority

  4. Mutating admission

    可以修改物件,也可以拒絕。例如 Priority admission 依 priorityClassName 填上 priority 數值與 preemptionPolicy。

    WAS bug 在這裡被拒
    Priority 外掛的 Admit() 發現衝突 → Forbidden

  5. Registry strategy:PrepareForCreate / Validate

    資源自己的處理邏輯:例如 feature gate 關閉時把欄位 drop 掉(dropDisabledPreemptionPolicyField),再做欄位格式與宣告式驗證。

    失敗
    422 Invalid

  6. Validating admission

    只能檢查、不能修改,用來做跨物件或政策類的規則(包括 ValidatingAdmissionPolicy / webhook)。

    失敗
    通常 403 Forbidden

  7. 寫入 etcd

    全部通過才會存進去;controller 與 scheduler 這時才 watch 得到這個物件。

    之後
    kube-scheduler 才看得到 PodGroup

校正(對照 upstream 原始碼):原本的整理說「比對設定與 PriorityClass 是否衝突」發生在 validating admission。實際上 Priority 外掛(plugin/pkg/admission/priority/admission.go)對 PodGroup 的處理寫在 Admit(),也就是 mutating 階段:同一個函式先填值、遇到衝突就直接回 Forbidden。它的 Validate() 只處理 PriorityClass 本身的建立與更新。

另外,Priority 外掛只在 Create 時處理 PodGroup(Pod 則是 Create 與 Update)。這也是 PodGroup 建立後 priority 欄位就固定的原因之一。

2. Mutating vs Validating admission

MutatingValidating
能不能改物件能不能
能不能拒絕能能
執行順序先(在 schema 驗證之前)後(看到的是最終物件)
內建例子Priority(Admit)、DefaultStorageClass、ServiceAccountPriority(Validate,只管 PriorityClass)、ResourceQuota
自訂方式MutatingWebhookConfiguration、MutatingAdmissionPolicyValidatingWebhookConfiguration、ValidatingAdmissionPolicy

同一個 admission 外掛可以同時實作兩種介面,Priority 就是。所以「某個外掛屬於 mutating 還是 validating」要看它的哪個方法處理哪種資源。

3. 對應到 WAS 的 upstream bug

overview 筆記第 9 節的 bug,完整發生在 operator 送出 Create(PodGroup) 的這一趟請求裡:

  1. Operator 送出請求:KubeRay 用 client 建立 PodGroup,只帶 priorityClassName,preemptionPolicy 是 nil。
  2. API defaulting:SetDefaults_PodGroup 先把 preemptionPolicy 補成 PreemptLowerPriority。
  3. Priority admission(mutating):從 PriorityClass 算出 Never,發現物件上已有不同的值 → 回 Forbidden。
  4. 請求被拒絕:PodGroup 沒有寫進 etcd,kube-scheduler 也就看不到它,整個 gang 排不起來。

apiserver 回的錯誤

the string value of PreemptionPolicy (PreemptLowerPriority) must not be provided in
pod group spec; priority admission controller computed Never from the given
PriorityClass name
  • Pod 為什麼沒事:Pod 的 preemptionPolicy 沒有 API defaulting,第 2 步什麼都不做,第 3 步直接從 class 填上。
  • upstream 修法(#143253):拿掉第 2 步的 defaulting,讓 PodGroup 走跟 Pod 一樣的流程。
  • KubeRay 的 workaround(resolvePreemptionPolicy):在第 1 步就把 Never 明確填好,第 2 步看到非 nil 就不動,第 3 步比對一致就通過。
