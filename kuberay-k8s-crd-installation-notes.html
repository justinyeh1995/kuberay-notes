CRD Installation

整理自 2026-11-02 的問答 · 對照 KubeRay repo 驗證 · 相關筆記:Operator RBAC · API Codegen Workflow

一句話:安裝 CRD 是部署階段的工作,不是 operator 執行時的工作。operator 的 Pod 啟動之前,CRD 就已經被 Helm、kustomize 或 envtest 送進 apiserver 了。

  • KubeRay operator 的 RBAC 沒有 customresourcedefinitions 的權限,它自己也裝不了 CRD。
  • CRD YAML 的來源都是 make manifests(controller-gen)產生的 config/crd/bases/,Helm chart 的 crds/ 是從這裡同步過去的。

1. 三種把 CRD 送進 apiserver 的途徑

途徑指令CRD 從哪來怎麼送進去
Helm(使用者)helm install kuberay-operator kuberay/kuberay-operatorhelm-chart/kuberay-operator/crds/Helm 3 在 render templates 之前先建立 crds/ 裡的 CRD
kustomize(開發)make install
make deploy		config/crdinstall:只送 CRD
deploy:CRD 跟 Deployment 一起送
envtest(測試)go testconfig/crd/bases測試框架啟動假的 apiserver 時讀 CRDDirectoryPaths 載入

Helm

Helm 3 對 chart 裡的 crds/ 目錄有特殊處理:install 時會先建立 CRD,再部署 templates(包含 operator 的 Deployment)。KubeRay 的 chart 裡有四個 CRD:

helm-chart/kuberay-operator/crds/
  ray.io_rayclusters.yaml
  ray.io_raycronjobs.yaml
  ray.io_rayjobs.yaml
  ray.io_rayservices.yaml

Helm 的坑:crds/ 只在 helm install 時建立。helm upgrade 不會更新 CRD,helm uninstall 也不會刪除 CRD。升級 KubeRay 版本時,如果新版的 CRD 多了欄位,要另外手動 kubectl apply --server-side 新的 CRD,否則 apiserver 會把新欄位剪掉(pruning)。

kustomize / Makefile

ray-operator/Makefile

install: manifests kustomize
	($(KUSTOMIZE) build config/crd | kubectl create -f -) || ($(KUSTOMIZE) build config/crd | kubectl replace -f -)

deploy: manifests kustomize
	cd config/default && $(KUSTOMIZE) edit set image kuberay/operator=${IMG}
	$(KUSTOMIZE) build config/default | kubectl apply --server-side=true -f -
  • install 用 create,失敗才改用 replace,不是 apply。原因是 CRD 太大,client-side apply 的 last-applied-configuration annotation 會超過 256KB 上限。
  • deploy 不會先跑 install。config/default/kustomization.yaml 本身就引用了 ../crd,所以 CRD 和 Deployment 在同一次 kubectl apply 送出(kustomize 會把 CRD 排在最前面)。這裡用 --server-side 也是為了避開同一個 annotation 大小限制。
  • KubeRay 的 Makefile 沒有 make run(kubebuilder 預設模板才有)。

envtest

ray-operator/controllers/ray/suite_test.go:82

CRDDirectoryPaths: []string{filepath.Join("..", "..", "config", "crd", "bases")},

envtest 啟動真的 etcd + kube-apiserver binary,但沒有 controller-manager 和 scheduler。CRD 由測試框架在啟動後主動安裝,等 CRD 變成 Established 才開始跑測試。pkg/webhooks/v1/suite_test.go 也是同樣的寫法。

2. 為什麼 operator 不在啟動時自己安裝 CRD?

operator 開機時順便 apply CRD 不是比較方便嗎?

  • 權限最小化:CRD 是 cluster-scoped 資源,能建立或修改 CRD 就等於能改變整個 cluster 的 API。operator Pod 被攻破時,這個權限的影響範圍太大。KubeRay 的 ClusterRole 裡確實沒有 customresourcedefinitions。
  • 職責分離:operator 負責 reconcile CR 的實例;API 的 schema 屬於 cluster 管理員或套件管理工具(Helm、OLM、ArgoCD)。
  • 多個 operator 的版本衝突:如果 cluster 裡跑了兩個不同版本的 operator(例如不同 namespace),各自開機時 apply 自己的 CRD,就會互相覆蓋。由部署工具統一管理 CRD 才能避免這種情況。

反過來看:operator 啟動時如果 CRD 還不存在,controller-runtime 建立 informer 會失敗(no matches for kind "RayCluster"),manager 起不來。這也是「CRD 一定要在 operator 之前安裝」的直接原因。
