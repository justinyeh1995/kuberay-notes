Ray PR #65763 · idle termination finalizer

resourceVersion Guard Notes

整理自 2026-09-23 的問答 · 起點是 rueian 的 review comment r4077182942

一句話:finalizer_patch 依照「之前讀到的」finalizers 決定要送 add /metadata/finalizers 還是 add /metadata/finalizers/-。讀取之後如果有人加了 finalizer,前者會把整個陣列換掉,別人的 finalizer 就被默默蓋掉。

  • 修法:在 add 前面加 {"op": "test", "path": "/metadata/resourceVersion", "value": <讀到的 rv>}。物件改過,整個 patch 就被拒。
  • 被拒時回 422,不是 409:apiserver 原始碼寫死的,本地 kind cluster 也實測過。
  • 收到 422 的處理:記 warning、return、不送 DELETE,下一輪 reconcile 用新快照重試。

1. 為什麼 rueian 說會蓋掉 finalizer

原本的程式碼哪裡有 race?

_delete_idle_ray_cluster 從 self._ray_cluster 拿 finalizers。這是上一次 _sync_with_api_server 的快取,讀取到送出 patch 之間有時間差。finalizer_patch 依照這份快照選路徑:

快照裡的 finalizers送出的 op讀取後有人加了 finalizer
非空add /metadata/finalizers/-(append)沒事,仍然是 append
空或不存在add /metadata/finalizers 值為 [ours]整個陣列被換成 [ours],回 200、沒有任何錯誤

關鍵在 RFC 6902:對已經存在的 object member 做 add,效果是取代它的值。反方向(快照有、實際被移除)時 /- 會因為 path 不存在而失敗,至少是會報錯的失敗。

finalizer 被蓋掉的後果:擁有那個 finalizer 的 controller 在刪除時不會被等待,它的清理邏輯(例如 GCS FT 的 Redis cleanup)會被跳過。

2. JSON Patch 的 test op

test 是什麼?

JSON Patch(RFC 6902)六種 op 之一,另外五種是 add、remove、replace、move、copy。test 不修改任何東西,只斷言某個 path 的值等於給定的 value。

重點是 JSON Patch 是原子的:一個 patch 是一組 op,依序套用,任一個失敗,整個 patch 都不生效。所以把 test 放最前面,就等於替後面的 op 加上前置條件:

[
  {"op": "test", "path": "/metadata/resourceVersion", "value": "123456"},
  {"op": "add",  "path": "/metadata/finalizers", "value": ["ray.io/idle-termination-cleanup-finalizer"]}
]
  • rv 還是 123456 → 物件沒被改過 → add 生效
  • rv 變了 → test 失敗 → 整個 patch 被拒,add 不會執行

為什麼用 resourceVersion?

K8s 每次修改物件都會更新 metadata.resourceVersion,可以當成快照的版本號。這就是 optimistic locking:不先上鎖,寫入時比對版本,衝突就重讀再試。可以想成 JSON Patch 版的 compare-and-swap。

rueian 留言裡的 "123456" 只是示意。實際的值必須取自讀 finalizers 的同一份快照(self._ray_cluster["metadata"]["resourceVersion"])。

3. 422 還是 409

被拒時回什麼 status code?文件有寫嗎?

K8s 官方文件沒有寫,但 apiserver 原始碼是寫死的。staging/src/k8s.io/apiserver/pkg/endpoints/handlers/patch.go 的 (p *jsonPatcher) applyJSPatch:

patchedJS, err := patchObj.Apply(versionedJS)
if err != nil {
    return nil, nil, errors.NewGenericServerResponse(http.StatusUnprocessableEntity, "", schema.GroupResource{}, "", err.Error(), 0, false)
}
  • v1.26.0 · L366–L393(本地 kind cluster 的版本)
  • master @ cc213a1 · L400–L427

任何 JSON Patch 套用錯誤都會變成 422,不只 test 失敗。test 的比對邏輯和「一個失敗就整個中止」的行為,在 github.com/evanphx/json-patch 這個套件裡實作;apiserver 只負責把錯誤轉成 422。

同一個檔案約 L814 的 interpretStrategicMergePatchError 也會回 422,但那是 strategic merge patch 的路徑,跟 JSON Patch 無關。

規範怎麼說?

  • RFC 6902(JSON Patch):只規定 test 失敗要中止整個 patch,沒有指定 HTTP code。
  • RFC 5789 §2.2(HTTP PATCH):patch 無法套用時建議回 422,狀態衝突時建議回 409。K8s 在這裡選了 422。

那 409 是什麼情況?

K8s 文件講 optimistic concurrency 時提到的 409 Conflict,是另一條路徑:用 PUT,或在 merge patch 的 body 裡帶 metadata.resourceVersion,由儲存層比對版本。我們用的是 JSON Patch 的 test op,比對發生在套用 patch 時,所以回 422。

4. 本地實測

在 kind-1-26-cluster(apiserver v1.26.0)的臨時 namespace 裡用 ConfigMap 測。所有資源的 JSON Patch 都走同一段 patch.go,CRD 也一樣,所以結果可以直接套用到 RayCluster。

情境HTTP結果
A · JSON Patch,test 帶錯的 rv422 Invalid整個 patch 被拒,finalizers 維持空的
B · JSON Patch,test 帶正確的 rv200["example.com/x"] 加上
C · merge patch 帶舊的 metadata.resourceVersion409 Conflict儲存層判定版本衝突
D · 不加 test,已有 finalizer 時 add /metadata/finalizers200["example.com/x"] 被覆蓋成 ["ray.io/ours"]

D 就是 rueian 說的 bug 的重現;A 證明加上 test 之後同樣情境會被擋下。

A 的 message 只有 the server rejected our request due to an error in our request,沒提到是 test op 失敗。所以在 warning 裡附上 e.response.text 幫助不大。

重現指令(A;B 把 value 換成當下的 rv)

kubectl create ns rv-test-ns
kubectl -n rv-test-ns create configmap rv-test --from-literal=a=b
kubectl proxy --port=18001 &
curl -i -X PATCH -H 'Content-Type: application/json-patch+json' \
  http://127.0.0.1:18001/api/v1/namespaces/rv-test-ns/configmaps/rv-test \
  -d '[{"op":"test","path":"/metadata/resourceVersion","value":"1"},
       {"op":"add","path":"/metadata/finalizers","value":["example.com/x"]}]'

# cleanup: remove finalizers first, otherwise the object can't be deleted
kubectl -n rv-test-ns patch cm rv-test --type=json -p '[{"op":"remove","path":"/metadata/finalizers"}]'
kubectl delete ns rv-test-ns

5. 程式碼改動

python/ray/autoscaler/_private/kuberay/node_provider.py

def finalizer_patch(
    finalizer: str, finalizers: Optional[List[str]], resource_version: str
) -> List[Dict[str, Any]]:
    ...
    # Guard the add with a resourceVersion test op: if the CR changed since it
    # was read, the apiserver rejects the whole patch instead of letting
    # "add /metadata/finalizers" replace finalizers added concurrently.
    resource_version_path = "/metadata/resourceVersion"
    return [test_patch(resource_version_path, resource_version), add_patch(path, value)]

python/ray/autoscaler/v2/instance_manager/cloud_providers/kuberay/cloud_provider.py

if IDLE_TERMINATION_CLEANUP_FINALIZER not in finalizers:
    resource_version = self._ray_cluster.get("metadata", {}).get("resourceVersion")
    if resource_version is None:
        logger.error(...)
        return
    payload = finalizer_patch(IDLE_TERMINATION_CLEANUP_FINALIZER, finalizers, resource_version)
    try:
        ...
    except requests.HTTPError as e:
        if e.response.status_code == 422:
            logger.warning(...)   # rejected; retry next reconcile cycle
        else:
            logger.exception(...)
        return
    except Exception:
        logger.exception(...)
        return

為什麼 None 檢查放在 if ... not in finalizers 裡面?

finalizer 已存在時不會送 patch,用不到 rv,應該可以直接 DELETE。只有要送 patch 的路徑才需要檢查。如果不擋,None 會變成 "value": null,每一輪都 422,永遠刪不掉,log 還會一直誤報衝突。

為什麼不寫 e.response is not None?

production 的 HTTPError 只會來自 raise_for_status(),一定帶 response。同一個函式處理 DELETE 404 時也沒加這個檢查,保持一致比較重要。

6. Python exception 備忘

  • 被 except 接住的 exception 就不會往外傳,除非自己再 raise。logger.exception 只記錄 traceback,不會重新丟出。
  • 接住之後程式會繼續往下跑,所以 422 分支裡的 return 才是擋住 DELETE 的關鍵。
  • 一個 try 後面多個 except 時,只會執行第一個符合的。在 except 裡 raise 不會被同一個 try 的其他 except 接住,會直接離開整個 try。
  • requests 的 exception 只從 keyword 讀 response:HTTPError(resp).response 是 None,HTTPError(response=resp).response 才有值。
  • 沒有專門給 422 用的 exception class,要看 e.response.status_code。

7. 測試

哪些測試要改?為什麼是這三個?

看的是「有沒有斷言 patch 的內容」,不是「是不是 delete 測試」。加了 test op 之後,只有斷言 get_patches(path) == [...] 的測試會受影響:

測試斷言 payload要改
delete_adds_finalizer_then_deletes有✅
delete_finalizer_appends_when_others_present有✅
delete_swallows_delete_failure有✅
delete_finalizer_idempotent不送 patch—
delete_swallows_patch_failurepatch 直接丟錯—
suspend_*走 merge patch—

resourceVersion = "123456" 設在共用的 get_basic_ray_cr()。另外兩個用到它的測試檔沒有斷言整個 metadata,不受影響。

_overwrite_patch_to_persist_finalizer 要改嗎?

不用。它不看 patch 內容,只記錄 patch 並把 finalizer 加進 CR。讓它去比對 test op,等於在 mock 裡重寫 apiserver,測到的會變成 mock 自己。

新測試 ..._delete_skips_delete_on_patch_conflict 為什麼斷言沒有 delete,而不是沒有 patch?

exception 是 mock 丟的,但丟出之後會不會 delete,取決於 production code。拿掉 422 分支的 return,程式就會一路跑到 DELETE,_deletes == [] 擋的就是這種回歸。反過來,mock 從不寫入 _patches,斷言「沒有 patch」永遠成立,只是在測 mock。

現有的 swallows_patch_failure 丟的是 RuntimeError,走 except Exception,沒有任何測試進得了新加的 except requests.HTTPError 區塊,所以值得保留這個測試。

命名採用檔案裡「情境 + 結果」的慣例。不叫 resource_version_mismatch,是因為測試只讓 mock 回 422,並沒有真的比對版本。

已知限制:沒有斷言 log,所以就算把 422 分支整個刪掉(改由 except Exception 接住),這個測試還是會過。要補的話,最直觀的是 mock.patch.object(cloud_provider.logger, "warning") 再 assert_called_once()。
