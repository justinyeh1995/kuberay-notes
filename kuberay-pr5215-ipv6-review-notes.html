一句話:Ray 2.56 起本身支援 IPv6,但 KubeRay 產生的設定寫死了 IPv4 假設(dashboard-host: 0.0.0.0、host:port 字串拼接、只適用 IPv4 的 SAN grep)。這個 PR 拿掉這些假設,方向正確;最大的問題是為了在 Pod 啟動時判斷 IP family 而在 KUBERAY_GEN_RAY_START_CMD 前面加了 eval,會弄壞現有使用者(包括 IPv4)。

  • 沒爭議的部分:net.JoinHostPort、mTLS 加 ::1、openssl verify -verify_ip、IPv6 CI job。
  • 主要疑慮:eval 前綴是 breaking change,已用 GKE / Azure 的真實範例證明。
  • 建議的替代:operator 在建 Pod 前從 head Service 的 spec.ipFamilies 判斷 family,直接寫 :: 或 0.0.0.0,就不需要 shell 片段和 eval。

3. eval 的問題(最重要)

為什麼會有 eval?

變數內容裡的 if、;、$VAR 在展開時只是普通文字,不會被執行。作者用 eval 強迫 bash 再解析一次。這只在「bash 裡不加引號展開 $KUBERAY_GEN_RAY_START_CMD」這一種寫法有效。

PR 產生的環境變數值

head:   eval if [[ "$KUBERAY_POD_IP" == *:* ]]; then export KUBERAY_DASHBOARD_HOST="::"; else ...; fi; ray start --head --dashboard-host=$KUBERAY_DASHBOARD_HOST ...
worker: eval ray start --address=... --block

真實專案實測(GitHub code search,本機模擬)

這個變數當初就是為了 #1560 的 wrapper 用途加的(把 KubeRay 產生的指令交給自己的程式執行)。eval 無條件加在所有 node 上,IPv4 cluster 一樣受影響。

最小重現(已放進 PR comment)

export X='eval if true; then echo yes; fi'

# exec ${KUBERAY_GEN_RAY_START_CMD}
bash -c 'exec ${X}'
# → bash: line 0: exec: eval: not found

# exec bash -lc "${KUBERAY_GEN_RAY_START_CMD}"
bash -c 'exec bash -lc "${X}"'
# → syntax error near unexpected token `then'

自己踩過的坑:X='...' 單獨一行而沒有 export,子 bash 看不到 X,exec 沒參數就直接成功,什麼都不印,看起來像「沒問題」。

替代方案:operator 事先決定 family

  • raycluster_controller.go:359 的 reconcile 順序是先 reconcileHeadService(365)再 reconcilePods(369)。
  • API server 會自動填 Service 的 spec.ipFamilies。KubeRay head Service 是 headless + 有 selector,預設 SingleStack,只有一個 family(已查 k8s v1.35 alloc.go 的 initIPFamilyFields)。
  • 改法:DefaultHeadPodTemplate / setMissingRayStartParams 多傳 family,直接填 :: 或 0.0.0.0;刪掉 pod.go:930-932 的片段和 :1340 的 eval。
  • 待作者評估:cache 時序(拿不到就 requeue 或用 0.0.0.0)、使用者自訂 head Service、函式簽名要改。
  • 作者當初沒這樣做的推測:一開始是 dual-stack 設計,看 Pod 自己的 IP 最準;改成 single-stack 後沒回頭檢討。

4. Ray 自動偵測 node IP

拿掉 node-ip-address 預設值後,Ray 2.56 會拿到正確的 IPv6 嗎?

看環境。src/ray/util/network_util.cc:291 GetNodeIpAddressFromPerspective:

  • head(scripts.py:1041,不帶位址):先 UDP connect 8.8.8.8:53(IPv4),失敗才試 [2001:4860:4860::8888]:53。
  • worker(scripts.py:1228,帶 head FQDN):依 head 位址的 family 選 v4 / v6。
  • kind 的 IPv6 Pod 沒有 IPv4 路由 → 8.8.8.8 失敗 → 拿到 Pod IPv6 ✅(作者就是在這裡驗證的)。
  • Pod 同時有 IPv4 link-local 介面(疑似 EKS IPv6 模式)→ 8.8.8.8 成功 → head 回傳 169.254.x.x ❌。
  • GetLocalhostIP(257)也是 IPv4 優先,影響 GCS 的 bind 位址。

建議文件寫上 workaround:node-ip-address: "$(KUBERAY_POD_IP)"(kubelet 展開,不依賴 eval)。

8. 最新版流程(2026-10-10,commit 4e0f947d)

一句話:operator 先建 head Service,API server 幫它填上 IP family,operator 建 head Pod 前讀這個 family,直接把 :: 或 0.0.0.0 寫進 ray start 的參數。判斷發生在 operator 裡,Pod 啟動時不再需要 shell。

dashboard-host 是怎麼決定的?

左邊色條:綠 = operator,灰 = API server,橘 = head Pod。右上角文字是同一個資訊。

走一次:IPv6-only cluster,rayStartParams 是空的

這就是 TestRayClusterIPv6 的情境(它刻意把 RayStartParams 清成空 map)。

  1. 使用者 apply RayCluster。reconcile 依 reconcileFuncs 的順序跑,reconcileHeadService 排在 reconcilePods 前面,所以先送出建 head Service 的請求。
  2. API server 收到的 Service 沒有 ipFamilies。cluster 是 IPv6-only,API server 存下來的物件就會是 ipFamilies: [IPv6]。
  3. 同一輪 reconcile 走到 reconcilePods,發現 0 個 head Pod,呼叫 createHeadPod。
  4. createHeadPod 第一件事是 getHeadServiceIPFamily。它用 label List head Service。如果 operator 的 cache 還沒看到步驟 1 建的 Service,這裡會回 error,reconcilePods 把它包成 ErrFailedCreateHeadPod,這一輪結束,下一輪再來。看得到時,GetServiceIPFamily 回傳 IPv6。
  5. family 一路傳到 setMissingRayStartParams。rayStartParams 裡沒有 dashboard-host,所以填入 defaultDashboardHost(IPv6) = "::"。
  6. generateRayStartCommand 把參數組成 ray start --head --dashboard-host=:: … --block 寫進 Pod spec。Pod 起來後直接執行這行。
  7. dashboard 在所有 IPv6 介面 listen。之後 operator 和 submitter 用 <head-svc>.<ns>.svc.<domain>:8265 這個 DNS 名稱連進來,DNS 回 AAAA 記錄,連得到。

IPv4 cluster 走同一條路,有什麼不同?

步驟 2 填的是 [IPv4],步驟 5 填 0.0.0.0,和 PR 之前的結果一樣。IPv4 使用者看得到的差別有兩個:

  • 建 head Pod 前多一次 List Service,找不到 Service 時會晚一輪才建 Pod。
  • head container 的 RAY_ADDRESS 從 127.0.0.1:6379 變成 localhost:6379。

步驟 5 只在使用者沒設 dashboard-host 時才生效。helm chart 和 samples 裡寫死 dashboard-host: "0.0.0.0" 的設定,拿到 IPv6-only cluster 上不會自動變成 ::(第 5 節提過,仍然成立)。
