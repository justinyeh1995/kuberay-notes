WAS PriorityClass & PreemptionPolicy

整理自 2026-10-21 ~ 10-24 的問答 · PR kuberay#5422(@alimaazamat)· branch kubernetes-was-priority-preemption(base 9dc55272)· 相關筆記:Kubernetes WAS Overview(整體脈絡)、Priority and Preemption(概念)、Node Label Delivery、Operator RBAC(Helm / Kustomize 權限)、Gang Scheduling Mechanics、Apiserver Admission Flow

一句話:這個 PR 讓 KubeRay 的 Kubernetes WAS(gang scheduling)把 RayCluster 的 priorityClassName / preemptionPolicy 複製到 Workload 與 PodGroup,讓整個 gang 可以用 Never 不搶佔。方向正確,但繞過 upstream bug 的方式只覆蓋了一半,而且有兩個會「卡住整個 RayCluster」的失敗路徑。

  • 不需要加 validation rule 去檢查 K8s 1.37(已被 discovery 檢查涵蓋);但PodGroupPreemptionPolicy gate 查不到 —— 因為 apiserver 是「靜默 drop 欄位」而不是回錯,static rule 無從判斷。
  • 真正的缺口是 runtime 偵測 + 警告,不是 admission 規則。
  • 真正適合放 validation rule 的是 gang 一致性(head 與所有 worker group 的 priority 設定必須一致),operator 現在只抄 head 的值。

2. 需要加 validation rule 檢查 K8s 1.37 + PodGroupPreemptionPolicy 嗎?

要加 validation rule 檢查 k8s v1.37 加上 PodGroupPreemptionPolicy feature gate 有開嗎?還是已經做了?

結論:不需要加 webhook / CRD validation rule —— 但不是因為「已經做了」,而是這個檢查本來就抓不到東西。真正缺的是 runtime 的偵測與警告。

2.1 K8s 1.37 已經被涵蓋,不要再加 rule

  • kubernetes_was_v1alpha3.go:422 的 schedulingV1alpha3Available() 用 discovery 檢查 scheduling.k8s.io/v1alpha3 是否有被 serve。該 API version 只在 1.37 存在(1.36 是 v1alpha2,1.37 整個換成 v1alpha3),所以老叢集根本開不起 WAS。
  • client library 已經是 k8s.io/api v0.37.0(ray-operator/go.mod:24)。
  • 想要 belt-and-braces 的話 repo 已有 pattern:ray-operator/main.go:239-252 用 utils.IsK8sVersionAtLeast()(controllers/ray/utils/util.go:995)檢查 SidecarSubmitterRestart 需要 K8s 1.35+。

2.2 PodGroupPreemptionPolicy gate:查不到,而且 static rule 無法判斷

上游(K8s 1.37)對 PodGroup.spec.preemptionPolicy 的處理順序:

  1. API 型別標記

    k8s.io/api/scheduling/v1alpha3/types.go:234:+k8s:ifDisabled("PodGroupPreemptionPolicy")=+k8s:forbidden

    看起來像會被拒絕
    但下一個步驟讓這條規則失效

  2. PrepareForCreate 先把欄位 drop 掉

    pkg/registry/scheduling/podgroup/strategy.go → dropDisabledPreemptionPolicyField
    pkg/registry/scheduling/workload/strategy.go → dropDisabledPGPreemptionPolicyFields

    gate 關閉時是靜默丟棄
    不是 Forbidden,不是錯誤

  3. 驗證才輪到 declarative rule

    rest.BeforeCreate 順序是 PrepareForCreate → Validate → declarative validation(k8s.io/apiserver/pkg/registry/rest/create.go:128-163)

    forbidden 規則看不到欄位
    所以不會觸發

結果:gate 關掉時 create 會成功,欄位被靜默丟棄,沒有任何 error 可以回報。所以 CRD / webhook validation rule 無從判斷(RayCluster webhook 也無從查 apiserver feature gate)。唯一症狀是「使用者要 Never,gang 還是在搶佔,而且完全沒有提示」。

文件寫法也不準:docs/guidance/kubernetes-was.md 說「the PodGroup's preemptionPolicy is left unset」,但其實是 operator 有設(kubernetes_was_v1alpha3.go:133,182),是 apiserver drop 掉的。結果一樣,但歸因錯了對象。

2.3 建議補的 runtime check(二選一)

  • A. create 後 read-back:operator 設了 policy 但存回去的 PodGroup 沒有 → gate 沒開 → log warning + 對 RayCluster emit Event。便宜,不需額外 API。
  • B. 啟動時一次性偵測(比照 main.go:239):用 server-side dry-run create 一個帶 preemptionPolicy 的 PodGroup,看回來的物件欄位是否被 strip 掉。

2.4 PR 繞過的 upstream bug 是真的(這部分做對了)

  • pkg/apis/scheduling/v1alpha3/defaults.go 的 SetDefaults_PodGroup:gate 開且欄位為 nil 時,在 admission 之前就把 preemptionPolicy default 成 PreemptLowerPriority。
  • plugin/pkg/admission/priority/admission.go 的 admitPodGroup:再從 PriorityClass 算出真正 policy,若與物件上的值不同 → Forbidden。

apiserver 回的錯誤

the string value of PreemptionPolicy (PreemptLowerPriority) must not be provided in
pod group spec; priority admission controller computed Never from the given
PriorityClass name

所以「create 之前顯式把欄位寫對」是正確的 workaround。

3. PriorityClass 不是 namespaced resource 對吧?

PriorityClass 不是 namespaced resource 對吧?

對,PriorityClass 是 cluster-scoped(跟 StorageClass 同類)。k8s.io/api/scheduling/v1/types.go:25 標了 +genclient:nonNamespaced,沒有 namespace 欄位。

3.1 對這個 PR 的影響

  • resolvePreemptionPolicy 用 client.ObjectKey{Name: priorityClassName}(不帶 namespace)✔ 正確。
  • Helm 只能用 ClusterRole + ClusterRoleBinding。PR 的 helm-chart/kuberay-operator/templates/priorityclass_role.yaml 有做對,註解也說明「即使 singleNamespaceInstall=true 仍然 cluster-scoped」→ 代表叢集層級的讀權限無條件增加,跟 operator 只 watch 哪個 namespace 無關,Role 無法縮小範圍(namespace 對 cluster-scoped resource 沒有意義)。
  • Dev overlay patch 的 target 是 ClusterRole(ray-operator/config/overlays/kubernetes-was-v1alpha3/kustomization.yaml:21-25)✔ 沒問題。
  • 為什麼需要 list + watch:operator 用的是 mgr.GetClient()(cached client,main.go:333),Get 會啟動 cluster-scoped informer,把整個叢集的 PriorityClass 都 cache 進 memory。改用 mgr.GetAPIReader()(uncached)就只需要 get,也不會快取全叢集 PriorityClass。

3.2 額外發現:globalDefault PriorityClass 的邊界情況(PR 沒涵蓋)

PriorityClass 是 cluster-scoped ⇒ globalDefault: true 是叢集層級概念。operator 的 workaround 只涵蓋「head pod 明確指定 PriorityClass」,漏掉「沒指定」的路徑:

  1. head pod 沒設 priorityClassName

    operator 傳空字串 → resolvePreemptionPolicy 直接回 nil(不查)

  2. apiserver defaulting(gate 開)

    SetDefaults_PodGroup 設成 PreemptLowerPriority

  3. Priority admission plugin

    establishPriority("") fallback 到 globalDefault 的 PriorityClass;若該 class policy 是 Never → 與 defaulting 值不一致 → Forbidden

    PodGroup 建不起來
    gang scheduling 讓整個 RayCluster 卡住

這是「叢集層級設定」觸發的,使用者自己完全沒設任何 priority 設定。而且 globalDefault 的 PriorityClass 只允許一個(priority admission plugin 的 validatePriorityClass 會擋第二個),所以是「全叢集單點」風險,影響所有沒設 priorityClassName 的 RayCluster。

修法建議:priorityClassName 為空時也要查 globalDefault 的 PriorityClass 決定要寫進 PodGroup 的 policy(或一律把 PodGroup 的 preemptionPolicy 設成 apiserver 實際會解析出的值)。目前 upstream 這個 defaulting-before-admission 的 bug 只被繞過了一半。

對照:Pod 沒有同樣問題。SetDefaults_Pod / SetDefaults_PodSpec 完全不碰 preemptionPolicy,一律留給 Priority admission plugin 從 class 解析,所以 globalDefault + Never 對 pod 一直正常。

5. #4 詳情:真正值得加 validation rule 的地方

operator 只把 head 的 priority 欄位複製到 Workload template / PodGroup:

priorityClassName := rayCluster.Spec.HeadGroupSpec.Template.Spec.PriorityClassName

但 kube-scheduler 要求 PodGroup 內所有 pod 的 priority / preemptionPolicy 一致:

  • all pods in a single pod group should have the same priority as the pod group
  • all pods in a single pod group should have the same preemption policy as the pod group's preemption policy

所以 worker group 用了不同(或沒用)priorityClassName 的 RayCluster 會變成永久排不上去的 gang,只有 scheduler 的模糊錯誤。可以在 ray-operator/pkg/webhooks/v1/raycluster_webhook.go:49(validateRayCluster)加一條:head 與所有 worker group 的 priorityClassName / pod-level preemptionPolicy 必須一致,否則 admission 直接擋掉。

6. new(expr) vs ptr.To(...)

preemptionPolicy = new(schedulingv1alpha3.PreemptionPolicy(*p)) vs ptr.To(...)?

結論:效果相同;在這個 repo 的 production code 用 new(...) 才符合規範,PR 寫法沒問題。(buildSchedulingResources,kubernetes_was_v1alpha3.go:267 起)

6.1 語意

preemptionPolicy = new(schedulingv1alpha3.PreemptionPolicy(*p))   // Go 1.26 起支援 new(expr)
preemptionPolicy = ptr.To(schedulingv1alpha3.PreemptionPolicy(*p)) // k8s.io/utils/ptr
  • 兩者都配置一個新變數、把值複製進去、回傳指標。ptr.To 的實作就是 func To[T any](v T) *T { return &v }。
  • new(expr) 是語言功能,不用 import;ptr.To 是函式,舊版 Go 也能用。編譯後基本相同。

6.2 KubeRay 的規範與時間線

時間事件
Go 1.26 之前new 只能接型別。要「指向某個值的指標」只能用 helper:早期 pointer.Int32(...) 等分型別函式,後來統一成泛型 ptr.To
d7855fbec(#4597)KubeRay 升到 Go 1.26(ray-operator/go.mod:go 1.26.0)
11de28835(#5019,2026-07-24).golangci.yml 開啟 modernize 的 newexpr 檢查,當時被標出的 ptr.To 全改成 new(...)
  • 現況:非測試程式碼有 9 處 new(expr)(例如 rayservice_controller.go:1095 new(gwv1.Namespace(...)))。
  • 仍有 ptr.To:非測試 7 處(例如 raycluster_controller.go:1880 ptr.To[int32](0))、測試約 205 處(本 PR 的測試也用 ptr.To,與其他測試一致)。推測是 newexpr 沒標出的形式,例如帶明確型別參數;analyzer 確切規則未查證。
  • review 時不需為此提意見:CI 會跑 golangci-lint,該改的會被抓。

6.3 為什麼印象中都是 ptr.To

  • 讀的是 2026-07 以前的 KubeRay:當時 production code 全是 ptr.To。
  • 讀的是測試:到現在還有大量 ptr.To。
  • 讀的是其他 K8s 生態專案:kubernetes/kubernetes、controller-runtime、多數 operator 用 ptr.To 很久了,要等它們的 Go 升到 1.26 才能改。

判斷方式:看該 repo 的 go.mod。1.26 以上且有開 newexpr → 用 new(expr);否則用 ptr.To。

6.4 真正要注意的是「複製」

corev1.PreemptionPolicy 與 schedulingv1alpha3.PreemptionPolicy 底層都是 string,Go 也允許直接轉指標型別:

preemptionPolicy = (*schedulingv1alpha3.PreemptionPolicy)(p) // 能編譯,但不要這樣寫

這樣 Workload / PodGroup 的欄位會和 RayCluster spec 共用同一塊記憶體。RayCluster 通常來自 controller-runtime 的 cache,共用指標可能在之後修改時改到 cache 裡的物件。PR 用 new(T(*p)) 先解參考再複製,沒有這個問題;換成 ptr.To 也一樣安全,兩者只是風格差異。

7. 這個功能跟 Ray autoscaler 的關係

這功能跟 autoscaler 的關係是什麼?

結論:目前互斥,沒有交集。開了 Ray autoscaler 的 RayCluster 完全不進 WAS,所以這個 PR 的 priority / preemption 設定也碰不到它。

7.1 程式碼怎麼寫

  • schedulingSkipReason(kubernetes_was_v1alpha3.go:386-397):enableInTreeAutoscaling: true 就回傳 "autoscaling is not yet supported",旁邊有 TODO: support the Ray autoscaler with workload-aware scheduling.
  • DoBatchSchedulingOnSubmission(:55-68):要跳過時不建 Workload / PodGroup,已存在的還會被 CleanupOnCompletion 刪掉。
  • 文件:docs/guidance/kubernetes-was.md:25、:133、:164 都寫明 autoscaling cluster 不做 gang scheduling。

7.2 對這個 PR 的影響

  • autoscaling cluster 沒有 PodGroup → 不會呼叫 resolvePreemptionPolicy,也不會查 PriorityClass。
  • pod 本身仍帶 template 的 priorityClassName,照一般 Pod 的 priority / preemption 規則逐 pod 排程,只是不整組排。

7.3 為什麼現在不支援

gang 大小是固定算的:minCount = 1 + CalculateDesiredReplicas(:244)。autoscaler 改 replicas → minCount 跟著變 → syncPodGroup 發現 minCount 不同就刪掉 PodGroup 重建(:203)。autoscaler 持續調整大小時 PodGroup 會反覆重建,所以目前直接排除。原地 resize gang 是 #5266 在處理的方向。

7.4 將來整合時跟這個 PR 有關的點

  • Never 的 gang 擴容會變慢:autoscaler 擴出來的新 pod 資源不夠時只會排隊,不會搶其他 workload。這正是 Never 的目的,代價是擴容延遲。
  • worker 必須和 PodGroup 的 priority / policy 一致(:269 的註解:kube-scheduler 要求一致)。目前只抄 head template,worker group class 跟 head 不同的問題(見第 5 節)會更明顯,整合 autoscaler 時更該處理。

Ray autoscaler ≠ Cluster Autoscaler。上面講的都是 Ray autoscaler(調 worker pod 數)。node 層的 Cluster Autoscaler 跟這個 PR 沒有直接的程式碼關係;它能不能看懂 PodGroup、一次替整個 gang 加夠 node,未查證。

8. syncWorkload 什麼時候跑?sync 在保護什麼?

syncWorkload 看起來在 reconcileRayCluster 跟 RayJob initializing 時會用到,所以每一次 reconcile 會用到的只有 RayCluster?sync 是為了確保使用者中途 patch、或其他東西改到 PriorityClass 跟 policy 嗎?

結論:只有 RayCluster reconcile 會真的跑到 syncWorkload,而且不是每次都會走到。sync 不是在防 priority / policy 被改:它只看 template 名稱和 minCount,priority 相關欄位完全沒有比對。

8.1 兩個呼叫點

呼叫點傳入WAS 的結果
raycluster_controller.go:993(reconcilePods 內)*RayCluster→ syncSchedulingResources → syncWorkload + syncPodGroup
rayjob_controller.go:201(RayJob initializing)*RayJob開頭 object.(*rayv1.RayCluster) 型別斷言失敗就 return nil(kubernetes_was_v1alpha3.go:56-59),不會呼叫 syncWorkload

RayJob 呼叫這個 hook 是給 Volcano / YuniKorn 這類要在 RayJob 層建 PodGroup 的 scheduler 用的。WAS 只在 RayCluster 層處理;RayJob 建出來的 RayCluster 之後走自己的 reconcile,從 :993 進來。

8.2 RayCluster reconcile 也不是每次都走到

  • reconcile 最前面的 validation 不通過(:165-215)→ 整個 reconcile 結束。
  • cluster 已 suspend(:960,return nil // stop reconcilePods because the cluster is suspended)→ suspend 期間 Workload / PodGroup 不同步,符合文件「suspend 時保留,resume 沿用」。
  • Recreate upgrade 刪除所有 pod 的那一輪(:975 附近 return nil)。

8.3 每次走到的成本

  1. Get 現有 Workload。controller 有 Owns(Workload),推測讀的是 informer cache(k.cli 是否 cache-backed 未確認)。
  2. 找不到 → 這時才呼叫 resolvePreemptionPolicy 查 PriorityClass,然後 Create。這就是 e50c4ba4「limit PriorityClass lookups to resource creation」的效果。
  3. 找到且一致(isWorkloadStale = false)→ 直接 return,沒有寫入。
  4. 找到但過期 → 先刪 PodGroup,再刪 Workload,回 error 讓下一輪重建。

syncPodGroup(:175)同一套模式。穩定狀態下每次 reconcile 只有兩次 cache 讀取,沒有寫入,也不查 PriorityClass。

8.4 sync 真正在處理什麼

情況sync 的反應位置
Workload / PodGroup 不存在(第一次建立,或被人刪掉)建立;這時才查 PriorityClass:131、:181
叢集形狀變了(worker group、replicas → minCount 變)刪掉重建(Workload 不可變,只能重建)isWorkloadStale :398;syncPodGroup :203-213
同名物件不是自己 own 的回 error,不跟別人搶:145、:194
物件正在刪除等刪完再重試:148、:197

比對的只有:template 數量、template 名稱、minCount(Workload);minCount(PodGroup)。priorityClassName / preemptionPolicy 不在比對範圍內。

review 可以問的點:RayCluster 建好之後,如果改 head template 的 priorityClassName 或 preemptionPolicy,Workload / PodGroup 不會被更新,會一直留著舊值。之後新建的 pod(例如 worker 被替換)帶的是新 priority,和 PodGroup 不一致,kube-scheduler 會拒絕(見第 5 節的一致性錯誤)。要不要把這兩個欄位加進 stale 判斷,或在文件寫明「建立後修改 priority 不支援」,值得問作者。PodGroup 的 spec 是否允許原地更新未查證;Workload 依程式碼註解是不可變的。

  • system priority class 例外:system-node-critical(2,000,000,000)與 system-cluster-critical(2,000,001,000)大於 1e9,屬保留名稱,只有 system- 前綴的 class 允許超過上限(ValidatePriorityClass)。這兩個 class 的 preemptionPolicy 固定是 PreemptLowerPriority、globalDefault 不適用。
