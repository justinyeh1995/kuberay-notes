Gang Scheduling 怎麼運作

整理於 2026-10-23 · 來源:upstream release-1.37 的 pkg/scheduler/framework/plugins/gangscheduling/gangscheduling.go 與 KubeRay WAS plugin · 相關筆記:Kubernetes WAS Overview、Priority and Preemption、Apiserver Admission Flow

重點:gang scheduling 是兩邊分工。KubeRay 宣告「這組 pod 要一起排、至少幾個」;kube-scheduler 的 GangScheduling plugin 執行「沒湊滿就誰都不放行」。

  • 關卡 1 PreEnqueue:人數不到 minCount,連排程都不開始。
  • 關卡 2 Permit:排好了先預留不 bind,湊滿 minCount 才一起放行;5 分鐘湊不滿就退回重來。
  • KubeRay 把整個 RayCluster(head + 所有 worker group)當成一個 gang。

1. KubeRay 這邊:宣告這一組

  1. 建立 PodGroup,gang.minCount = 1 + 所有 worker 的 desired replicas(buildClusterSchedulingPolicy)。
  2. 在每個 pod 寫上 schedulerName: default-scheduler 與 spec.schedulingGroup.podGroupName,把 pod 掛到 PodGroup(AddMetadataToChildResource)。
  3. 叢集大小改變時,同步更新或重建 PodGroup,讓 minCount 跟著變。

KubeRay 就做這三件事,「一起排」的邏輯全在 scheduler。

2. kube-scheduler 這邊:兩道關卡

一般 pod 是一個一個排、排到一個就 bind 一個。gang 的 pod 多了兩道關卡:

  1. PreEnqueue:人數不夠先不排

    這組在佇列裡的 pod 數還沒到 minCount,pod 連排程都不會開始。KubeRay 還在一個個建 worker 時,scheduler 不會先把 head 排上去。

    狀態
    UnschedulableAndUnresolvable

  2. Filter / Score:照常找節點

    每個 pod 跟一般 pod 一樣挑節點。

    資源不夠時
    進入 preemption 判斷(見第 4 節)

  3. Permit:排好了也先不 bind

    找到節點後先預留資源(assumed),停在 Permit 等。預留數達到 minCount,一次放行所有等待中的 pod、同時 bind。

    逾時
    5 分鐘湊不滿 → 退回、釋放預留資源、之後重試

  4. Bind

    整組 pod 一起被綁到節點上。

    結果
    all-or-nothing

PreEnqueue

if allPodsCount < int(policy.Gang.MinCount) {
    return fwk.NewStatus(fwk.UnschedulableAndUnresolvable,
        "waiting for minCount pods from a gang to appear in scheduling queue")
}

Permit(permitTimeoutDuration = 5 * time.Minute)

if scheduledPodsCount < int(podGroup.Spec.SchedulingPolicy.Gang.MinCount) {
    return fwk.NewStatus(fwk.Wait, "waiting for minCount pods from a gang to be scheduled"), permitTimeoutDuration
}
// quorum 達成:放行這個 pod,並通知同組所有在等的 pod
waitingPod.Allow(Name)

2.1 什麼事件會讓被擋的 pod 重試

EventsToRegister 註冊的事件:

  • 有新的 pod 加入:可能正好湊滿 minCount。
  • PodGroup 的 minCount 變小:門檻降低,原本在等的 pod 可能就夠了。這和 @marosset 的 #5266(in-place gang resize)有關:縮小叢集時直接改 minCount,不必刪 PodGroup 重建。
  • PodGroup 被建立:pod 先建好、PodGroup 後到的情況。

未查證:1.37 是否另有「整組一起計算 placement」的機制(而不是逐 pod 排程再用 Permit 等待),沒有再往下查。本節描述的是 GangScheduling plugin 本身的行為。

3. 為什麼 KubeRay 把所有 worker group 放進同一個 gang

KubeRay 的設計是「一個 RayCluster 就是一個不可分割的工作單位」:head 加上所有 worker 湊齊才有用。gang scheduling 要防的是部分 pod 被排上、其餘卡住:

  • head 起來、worker 沒起來:Ray 叢集形式上存在,但工作要的 worker(例如 8 張 GPU)不夠,已起來的 pod 佔著節點和 GPU 卻沒在做事。
  • 多個 Ray 叢集各起一半:A、B 各拿一半 GPU,誰都湊不滿,互相卡住(deadlock)。
  • 切成多個 gang(例如 CPU 組、GPU 組各一個):CPU 組先排上、GPU 組還在等,又回到部分起來、白佔資源。

程式碼的註解也寫明:

// clusterPodGroupTemplateName is the name of the single PodGroupTemplate that
// gang schedules the entire RayCluster (head + all worker groups) together.

3.1 其他排程器 plugin 也是一樣

plugingang 範圍
Volcano一個 PodGroup,MinMember 是整個叢集的 pod 數(volcano_scheduler.go:70);另用 subgroup policy 處理 multi-host group 內部
YuniKornMinMember: CalculateDesiredReplicas(app) + 1 // +1 for the head pod(yunikorn_task_groups.go:65)
scheduler-plugins整個叢集一個 PodGroup
WAS一個 Workload template(cluster)、一個 PodGroup,涵蓋全部

WAS 第一次整合(#4962,aac52c96)的 commit 歷史裡有「Single gang scheduling w/ K8s v1alpha2 scheduling APIs」,代表討論後收斂成單一 gang。

3.2 這個設計的代價

  • 所有 pod 必須同一個 priority:scheduler 以整組為單位排序與決定搶佔,所以 head 與每個 worker group 的 PriorityClass 都要一致。KubeRay 目前只讀 head 的值,worker 不一致時整組會一直 Pending。
  • 不支援 autoscaling:worker 數一變,minCount 就得跟著變;WAS 遇到 enableInTreeAutoscaling: true 直接放棄 gang。
  • 不能先用部分 worker 開跑:有些工作少幾個 worker 也能先跑,但單一 gang 不允許。

上游 Workload 的 podGroupTemplates[] 其實可以定義多個 template(例如每個 worker group 一個 PodGroup)。KubeRay 只用一個,是設計選擇,不是 API 限制。改成每組一個,priority 只需「組內一致」,但又會回到部分起來、互相等待的風險。

4. 跟 priority / preemption 的關係

資源不夠、湊不滿 minCount 時,scheduler 要決定能不能搶別人的 pod 來騰空間,這時看 PodGroup 的 priority 與 preemptionPolicy:

  • Never:不搶,整組停在上面兩道關卡等待。
  • PreemptLowerPriority:可以驅逐較低 priority 的 pod 來湊滿。

這也是 PodGroup 的 priority 必須和 pod 一致的原因:scheduler 是以整組為單位做這個決定。詳見 Priority and Preemption。
