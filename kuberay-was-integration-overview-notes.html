KubeRay 脈絡整理 · Kubernetes WAS(Workload-Aware Scheduling)

Kubernetes WAS × KubeRay 全貌

整理於 2026-10-22(10-24 補 opt-in label、RayJob、label vs field)· branch kubernetes-was-priority-preemption(e50c4ba4)· 相關筆記:WAS PriorityClass & PreemptionPolicy(PR review 細節)、Operator RBAC(Helm / Kustomize 權限)、Gang Scheduling Mechanics、Apiserver Admission Flow

一句話:Kubernetes 1.37 把 gang scheduling 做進 in-tree(Workload + PodGroup API + 預設 kube-scheduler)。KubeRay 用 batch scheduler plugin 的形式接上它:每個 RayCluster 對應 一個 Workload + 一個 PodGroup,head 與所有 worker 都是同一個 gang,pod 透過 spec.schedulingGroup 掛上去。

  • 不用裝 Volcano / YuniKorn,pod 仍由 default-scheduler 排程。
  • KubeRay 端以 feature gate KubernetesWAS 開啟,RayCluster 再以 label ray.io/gang-scheduling-enabled: "true" opt in(值要是 "true",不分大小寫;RayJob 加在自己的 metadata 上即可,會複製到它建的 RayCluster)。
  • 目前進行中的工作:把 PriorityClass / preemptionPolicy 帶進 gang(本 branch),以及 upstream 修正 PodGroup 預設值 bug(kubernetes#143253)。

下文的程式碼路徑以 ray-operator/controllers/ray/ 為根;was_v1alpha3.go 指 batchscheduler/kubernetes-was/v1alpha3/kubernetes_was_v1alpha3.go。

2. Upstream:WAS 是什麼

  • Workload(scheduling.k8s.io/v1alpha3,namespaced):描述「這組工作要怎麼被排程」的模板。spec.podGroupTemplates[] 每個 template 有 schedulingPolicy(例如 gang.minCount),1.37 起還有 priorityClassName / preemptionPolicy。spec 幾乎不可變。
  • PodGroup(KEP-5832;v1alpha2 / 1.36 就已是獨立物件):runtime 物件,透過 spec.workloadRef 指回某個 Workload 的 template。kube-scheduler 以它為單位做 gang 決策;帶 finalizer scheduling.k8s.io/podgroup-protection,只要還有 pod 引用就擋住刪除。
  • Pod:spec.schedulingGroup.podGroupName 指向 PodGroup(不可變)。scheduler 會等到 PodGroup 湊滿 minCount 才一次放行。
  • Priority:priority admission 會從 priorityClassName 算出 PodGroup 的 priority 與 preemptionPolicy;scheduler 要求 PodGroup 內每個 pod 的 priority 與 PodGroup 一致。

叢集需求(KubeRay 文件 docs/guidance/kubernetes-was.md):

  • apiserver --runtime-config=scheduling.k8s.io/v1beta1=true,scheduling.k8s.io/v1alpha3=true(KubeRay 用 v1alpha3,但 kube-scheduler 的 GenericWorkload 整合要 v1beta1 也被 serve)。
  • GenericWorkload=true:apiserver、controller-manager、scheduler。
  • (選用)PodGroupPreemptionPolicy=true:要用 Never 時才需要。

4. Operator 與 scheduler 怎麼分工

這跟 operator 有關嗎?它歸在 batch-scheduler 底下。

有關,它就是 operator 的程式碼。batchscheduler 是 ray-operator 裡的 package,和 RayCluster controller 跑在同一個 process,不是另外部署的元件。開關是 operator 的啟動參數(--feature-gates=KubernetesWAS=true),權限用的是 operator 的 ServiceAccount — 所以 #5422 讀 PriorityClass 的 RBAC 加在 kuberay-operator Helm chart 的 ClusterRole 上。

ray-operator/                          ← kuberay-operator binary
└── controllers/ray/
    ├── raycluster_controller.go       ← RayCluster reconciler
    ├── rayjob_controller.go
    └── batchscheduler/                ← 排程器整合 adapter(plugin)
        ├── interface/                 ← BatchScheduler 介面
        ├── schedulermanager.go        ← 依設定挑一個 plugin
        ├── volcano/  yunikorn/  kai-scheduler/  scheduler-plugins/
        └── kubernetes-was/v1alpha3/

batchscheduler 這個名字容易誤會:裡面的程式碼不做排程,只負責 (1) 依各排程器的格式建立物件(Volcano 的 PodGroup、WAS 的 Workload + PodGroup),(2) 在 pod 寫上 schedulerName、label 或 schedulingGroup。實際決策由外部排程器做:

plugin實際排程的是誰需要另外裝?
volcano / yunikorn / kai-scheduler各自的 scheduler要
scheduler-plugins裝了 coscheduling plugin 的 scheduler要
kubernetes-wasK8s 內建 default-scheduler不用,但要開 K8s feature gate

4.1 兩層契約:interface 不是給 scheduler 用的

這些 scheduler plugin interface 實際上怎麼被 scheduler 使用?

不會被任何 scheduler 呼叫。呼叫它們的只有 KubeRay operator 自己;operator 和 scheduler 之間沒有函式呼叫,只透過 API 上的物件溝通。

┌─────────────── kuberay-operator process ───────────────┐
│  RayCluster / RayJob controller                         │
│        │ 呼叫 Go interface(BatchScheduler)            │
│        ▼                                                │
│  batchscheduler plugin(volcano / kubernetes-was / ...)│
└────────┬────────────────────────────────────────────────┘
         │ create / update / delete K8s 物件
         ▼
   kube-apiserver:Workload、PodGroup、Pod(schedulerName、schedulingGroup)
         ▲
         │ watch
   kube-scheduler(或 Volcano、YuniKorn 等)
  • Go interface(batchscheduler/interface/):operator 內部的抽象,讓 controller 不用知道背後是哪個排程器。
  • K8s 物件:operator 與 scheduler 真正的契約。scheduler 只認 pod.spec.schedulerName、pod.spec.schedulingGroup、PodGroup 的 minCount / priorityClassName 等欄位,不知道 KubeRay 存在。

4.4 容易混淆的名詞

名詞指的是
KubeRay 的 BatchScheduler interface、batchscheduler/*operator 內部的 adapter
KubeRay 的 batchscheduler/scheduler-plugins/其中一個 adapter,對接 kubernetes-sigs/scheduler-plugins 的 coscheduling
kube-scheduler 的 scheduling framework plugin(Filter、Score、PostFilter,例如 DefaultPreemption)跑在 scheduler process 裡的排程邏輯,跟 KubeRay 無關

5. 一次 RayCluster reconcile 會發生什麼

  1. 進 reconcilePods,先跑 DoBatchSchedulingOnSubmission

    raycluster_controller.go:993:每次 reconcile、在建立任何 pod 之前呼叫。回錯就整次 reconcile 中止並 requeue。

    錯誤即重試
    WAS 大量用「回 error 等下一輪」來排序刪除/重建

  2. 判斷要不要 gang

    was_v1alpha3.go:386 schedulingSkipReason:沒有 opt-in label,或 enableInTreeAutoscaling: true → 跳過,並呼叫 CleanupOnCompletion 把之前建的 Workload/PodGroup 刪掉。label 判斷是 strings.EqualFold(labels[...], "true")(:388):"True" 也算,"false" / 空字串 = 沒開。和 YuniKorn、scheduler-plugins 不同,那兩個只看 key 存不存在(yunikorn_scheduler.go:112、scheduler_plugins.go:112),寫 "false" 反而會開 gang。事後拿掉 label → 下一次 reconcile 走跳過路徑,清掉 Workload/PodGroup。

    autoscaling 不支援
    minCount 會跟著 replicas 跳,目前直接放棄 gang

    was_v1alpha3.go:114:先 buildSchedulingResources 算出期望狀態,再依序 syncWorkload(:125)、syncPodGroup(:175)。不存在就 create;存在但過期就刪掉等下一輪重建(見第 7 節)。

    PriorityClass lookup
    只發生在 create 分支(本 branch 新增)

    raycluster_controller.go:1648 / 1671 / 1695(head、worker、multi-host worker)→ AddMetadataToChildResource(was_v1alpha3.go:70):設 schedulerName: default-scheduler,以及 spec.schedulingGroup.podGroupName = <cluster>-cluster。

    不分 group

  5. kube-scheduler 做 all-or-nothing

    湊不滿 minCount 的話,所有 pod 一起留在 Pending。

    刪除 RayCluster
    靠 ownerReference GC 收掉 Workload/PodGroup

7. 叢集形狀改變時的處理

  • Workload 過期(isWorkloadStale,was_v1alpha3.go:398:template 數量/名稱或 minCount 不同):Workload 不可變,只能砍掉重建。順序是先刪 PodGroup(它引用 Workload)→ 回 error → 下一輪再刪 Workload → 回 error → 再下一輪重新 create 兩者。
  • PodGroup 過期(只比 gang.minCount):刪掉重建。
  • 刪 PodGroup 前先拔 finalizer(deletePodGroup,:216):否則還有 pod 引用時刪不掉,替換流程會卡住。
  • 刪除都帶 UID precondition(:381),避免誤刪同名的新物件。
  • 同名但不是自己 own 的物件:直接回錯,不跟別人搶(TODO:之後補 Warning event)。
  • Suspend:pod 刪掉但 Workload/PodGroup 保留,resume 時 pod 重新加入同一個 gang。
  • priority 欄位不參與 stale 判斷:建立後就固定,要換 PriorityClass 得重建 RayCluster(本 branch 文件已註明)。

8. 目前進行中:PriorityClass & preemption(#5422)

要解的問題:原本 Workload/PodGroup 不帶任何 priority,(1) 與 pod 的 priority 不一致,違反 scheduler 的要求;(2) 使用者無法讓整個 gang 以 Never 等待資源,只能用預設 PreemptLowerPriority 去搶。

做法:

  • buildSchedulingResources 把 head 的 priorityClassName / preemptionPolicy 寫進 template 與 PodGroup。
  • resolvePreemptionPolicy:policy 沒寫但有 class 時,create 前自己 GET PriorityClass 補上 policy(繞 upstream bug,見下節)。
  • 附帶:Helm priorityclass_role.yaml 與 kustomize overlay 加 cluster-scoped PriorityClass get/list/watch;kind 設定加 PodGroupPreemptionPolicy=true;docs、unit、e2e。

review 細節(gate 關閉時欄位被靜默 drop、globalDefault、gang 一致性驗證等)見 WAS PriorityClass & PreemptionPolicy。

8.1 解法的完整流程

解法是 buildSchedulingResources 把 pc + policy 填進去、建起來就有了?重點是填入 PodGroup spec 的 policy 避免被 API defaulting 改寫?

大致對,兩處要修正:受 API defaulting 影響的只有 preemptionPolicy,priorityClassName 沒有這個風險;重點也不是「避免被改寫」,而是「不要留空」。

① buildSchedulingResources:算出期望狀態(每次 reconcile 都跑,還沒送給 apiserver)

欄位來源寫到哪
priorityClassNamehead 的 spec.priorityClassNameWorkload template + PodGroup spec
preemptionPolicyhead 的 spec.preemptionPolicy,有寫才複製,否則 nil同上
priority(整數)KubeRay 不填由 Priority admission 依 class 填

② 誰呼叫 syncWorkload / syncPodGroup:路徑固定,RayCluster controller 每次 reconcile、建 pod 之前都會跑。

RayClusterReconciler.reconcilePods
  └─ raycluster_controller.go:993  scheduler.DoBatchSchedulingOnSubmission(rayCluster)
       └─ syncSchedulingResources          (was_v1alpha3.go:114)
            ├─ buildSchedulingResources    ← 算 desired
            ├─ syncWorkload                ← 先
            └─ syncPodGroup                ← 後

resolvePreemptionPolicy 只在「物件不存在、要 create」的分支執行;物件已存在時只檢查是否過期,不會再查 PriorityClass。

③ 重點:送出 Create(PodGroup) 時,preemptionPolicy 不能是 nil

送出時的 preemptionPolicyAPI defaultingPriority admission結果
nil(沒有 workaround)補成 PreemptLowerPriorityclass 是 Never → 不一致❌ Forbidden
Never(resolvePreemptionPolicy 預先查 class 填好)非 nil,不動class 是 Never → 一致✅ 寫入 etcd
  • 不是「避免被改寫」:defaulting 只補 nil,不改已有的值;admission 也不改寫,只比對、不一致就拒絕。workaround 是搶在 defaulting 之前填上正確的值。流程細節見 Apiserver Admission Flow。
  • priorityClassName 沒有這個問題:它沒有 API defaulting。
  • Workload 那邊其實不需要:Workload 沒有 preemptionPolicy defaulting,priority admission 也不處理 Workload;syncWorkload 裡的 lookup 只是讓兩邊值一致。

一句話:KubeRay 每次 reconcile 都算出 desired 物件;只有在 create PodGroup 那一刻,它才先查 PriorityClass 把 preemptionPolicy 明確填好,讓 apiserver 的 defaulting 沒機會補上和 class 衝突的 PreemptLowerPriority。

8.2 邊界情況:priorityClassName 為空時直接 return

resolvePreemptionPolicy 開頭 if preemptionPolicy != nil || priorityClassName == "" 會跳過 lookup。通常沒事:沒 class 可查,而且 admission 在沒有 globalDefault class 時算出的也是 PreemptLowerPriority,與 defaulting 一致。

例外:名稱空白時 admission 會改用 globalDefault PriorityClass(upstream establishPriority → getDefaultPriority)。若它是 preemptionPolicy: Never,同一個 bug 會讓 PodGroup 被拒。這種設定允許但罕見:default class 設 Never 只有在叢集刻意存在更低 priority 的 class 時才有作用。review 時以 nit 提出、請作者寫進 Limitations 即可。

9. Upstream bug 與修正

  1. API defaulting 先跑

    pkg/apis/scheduling/v1alpha3/defaults.go SetDefaults_PodGroup:gate 開且 preemptionPolicy 為 nil → 補成 PreemptLowerPriority。

    問題起點
    使用者沒填,卻被填了值

  2. priority admission 再比對

    plugin/pkg/admission/priority/admission.go admitPodGroup:從 PriorityClass 算出 Never,發現 spec 已有不同的值 → Forbidden。

    結果
    引用 Never class 又沒寫 policy 的 PodGroup 一律建不起來
  • upstream 修法(#143253,OPEN):移除 PodGroup(v1alpha3、v1beta1)與 CompositePodGroup(v1alpha3)的 preemptionPolicy defaulting,nil 留給 admission 依 PriorityClass 填,與 Pod 的流程一致;明確寫了衝突值仍會被拒。
  • KubeRay 何時能拿掉 workaround:修正 merge 且 KubeRay 支援的最低 K8s 版本都包含它之後(1.37 若沒 backport 就拿不掉)。可移除:resolvePreemptionPolicy 與兩個呼叫點、PriorityClass RBAC、文件中 lookup 相關限制。要保留:buildSchedulingResources 複製 class / 明確 policy 的邏輯。
  • Workload 不受此 bug 影響:upstream master 的 Workload 沒有 preemptionPolicy defaulting,priority admission 也不處理 Workload。所以 syncWorkload 裡的 lookup 是為了與 PodGroup 一致,不是 workaround。

這跟目前 KAI scheduler 的 gang scheduling 比有什麼差?

10.3 怎麼選

  • KAI:GPU 叢集、多團隊共用,需要 queue、配額、fair share 或 GPU 切分。KubeRay 端很薄,複雜度在 KAI 那側。
  • WAS:只要「整個 RayCluster all-or-nothing」,不想多裝、維運另一套 scheduler。代價是 alpha API、沒有 queue 與配額,KubeRay 要自己管 PodGroup 生命週期 — 這也是 WAS PR 會碰到 RBAC、finalizer、過期重建與 upstream defaulting bug 的原因。
  • 兩者在 KubeRay 只能擇一:ValidateBatchSchedulerConfig 會擋同時設定。

12. 為什麼 opt-in 用 label 而不是新的 field?

為啥是加 label 而不是一個新的 field?

結論:這個 label 不是 WAS 發明的,是沿用 2024-09 YuniKorn 整合留下的慣例;CRD 到現在都沒有對應 field(ray-operator/apis 裡沒有)。

12.1 歷史(有查證)

  • 來源:df5577fe1(#2396,2024-09-27)Support gang scheduling with Apache YuniKorn。
  • 原本提議叫 yunikorn.apache.org/gang-scheduling;@MortalHappiness 指出這個 label 只有 KubeRay 讀、YuniKorn 不讀,應該用 ray.io/ 前綴 → 改成 ray.io/gang-scheduling-enabled。
  • @andrewsykim 問值是否必須是 "true",作者回「存在就夠了」→ 這就是 YuniKorn(yunikorn_scheduler.go:112)與 scheduler-plugins(scheduler_plugins.go:112)只看 key 的由來。WAS 後來改成要求 "true"(kubernetes_was_v1alpha3.go:388),兩邊語意因此不一致。
  • 討論焦點是 label 的命名與值,沒看到「為什麼不用 field」的討論。

12.2 為什麼 label 合理(推論,PR 沒寫)

  • 不用動 CRD API:加 field 等於改 RayCluster 的 v1 API,要 API review、進相容性承諾,之後很難拿掉。label 是 metadata,適合 alpha 功能和還在演進的 integration。
  • 一個開關給所有 scheduler 共用:Volcano、YuniKorn、scheduler-plugins、WAS 都看同一個 label。做成 field 就得設計能涵蓋所有 scheduler 的 schema,而各家能力不同(queue、minResource、priority…)。
  • 和 batch scheduler 生態一致:那些 scheduler 本來就用 label / annotation 設定(yunikorn.apache.org/queue、kai.scheduler/queue)。
  • RayJob 免費支援:RayJob 本來就把所有 label 複製到它建的 RayCluster(rayjob_controller.go:1005-1006);做成 field 的話 RayJob / RayService 都要各自加欄位並往下傳。

12.3 代價

  • CRD 擋不到錯的值:CRD 的 OpenAPI schema 與 CEL(x-kubernetes-validations)對 metadata 只能看 name / generateName,碰不到 labels。目前 KubeRay 也沒有任何地方檢查這個 label 的值,寫成 "ture" 不會報錯,只會靜靜不生效。
  • 語意不一致:同一個 label,YuniKorn 看存在、WAS 看值,換 scheduler 時容易踩到。
  • 不好發現:kubectl explain 查不到,要讀文件才知道。

12.4 那 label 要在哪裡驗證?

機制能看 metadata.labels?KubeRay 現況
CRD OpenAPI schema / CRD CEL❌ metadata 只能約束 name、generateName—
Validating admission webhook✅ AdmissionReview 帶完整物件raycluster_webhook.go:49 只檢查 name 與 worker group,沒看 labels
ValidatingAdmissionPolicy(in-tree CEL)✅ object.metadata.labelsKubeRay 沒提供
controller 在 reconcile 時驗證✅raycluster_controller.go:165-215,每次 reconcile 都跑
  • webhook 預設沒有:只有環境變數 ENABLE_WEBHOOKS == "true" 才註冊(ray-operator/main.go:379)。Helm chart 裡沒有 ValidatingWebhookConfiguration 也沒設這個變數,所以 Helm 安裝一定沒有 webhook;只有 kustomize 的 ray-operator/config/default-with-webhooks/ 會開,而且要另外裝 cert-manager。
  • controller 驗證的行為:reconcile 一開始(setDefaults 之後)依序跑 ValidateRayClusterMetadata、ValidateRayClusterSpec、TLS / cert-manager、ValidateRayClusterUpgradeOptions、ValidateRayClusterStatus。不通過 → error log + Warning event + return ctrl.Result{}, nil:不 requeue、不建 pod、也不會走到 WAS hook,要等物件再被修改才會重跑。
  • 差別只在「什麼時候擋」:webhook 和 controller 呼叫的是同一組 utils.Validate*。webhook 在 admission 就拒絕;controller 版本是物件照樣寫進 etcd、kubectl apply 成功,但 operator 不動,使用者要看 kubectl describe 的 event 才知道原因。
  • 建議:如果要檢查 ray.io/gang-scheduling-enabled 的值,加在 controller 這層(例如 ValidateRayClusterMetadata)才對 Helm 使用者有效;只加在 webhook 大多數人碰不到。

field 相對 label 的好處因此可以說得更精確:CRD 自己就能擋,不需要額外部署 webhook;label 不是驗證不了,而是要靠 webhook、ValidatingAdmissionPolicy 或 controller 另外寫。

之後 gang scheduling 穩定下來,有可能升級成正式 field(例如 spec.gangScheduling),但目前沒查到相關 issue 或 KEP。
