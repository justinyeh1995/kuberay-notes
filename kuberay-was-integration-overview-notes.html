KubeRay 脈絡整理 · Kubernetes WAS(Workload-Aware Scheduling)

Kubernetes WAS × KubeRay 全貌

整理於 2026-10-22 · branch kubernetes-was-priority-preemption(e50c4ba4)· 相關筆記:WAS PriorityClass & PreemptionPolicy(PR review 細節)、Operator RBAC(Helm / Kustomize 權限)

一句話:Kubernetes 1.37 把 gang scheduling 做進 in-tree(Workload + PodGroup API + 預設 kube-scheduler)。KubeRay 用 batch scheduler plugin 的形式接上它:每個 RayCluster 對應 一個 Workload + 一個 PodGroup,head 與所有 worker 都是同一個 gang,pod 透過 spec.schedulingGroup 掛上去。

  • 不用裝 Volcano / YuniKorn,pod 仍由 default-scheduler 排程。
  • KubeRay 端以 feature gate KubernetesWAS 開啟,RayCluster 再以 label ray.io/gang-scheduling-enabled: "true" opt in。
  • 目前進行中的工作:把 PriorityClass / preemptionPolicy 帶進 gang(本 branch),以及 upstream 修正 PodGroup 預設值 bug(kubernetes#143253)。

下文的程式碼路徑以 ray-operator/controllers/ray/ 為根;was_v1alpha3.go 指 batchscheduler/kubernetes-was/v1alpha3/kubernetes_was_v1alpha3.go。

2. Upstream:WAS 是什麼

  • Workload(scheduling.k8s.io/v1alpha3,namespaced):描述「這組工作要怎麼被排程」的模板。spec.podGroupTemplates[] 每個 template 有 schedulingPolicy(例如 gang.minCount),1.37 起還有 priorityClassName / preemptionPolicy。spec 幾乎不可變。
  • PodGroup(KEP-5832,1.37 拆出):runtime 物件,透過 spec.workloadRef 指回某個 Workload 的 template。kube-scheduler 以它為單位做 gang 決策;帶 finalizer scheduling.k8s.io/podgroup-protection,只要還有 pod 引用就擋住刪除。
  • Pod:spec.schedulingGroup.podGroupName 指向 PodGroup(不可變)。scheduler 會等到 PodGroup 湊滿 minCount 才一次放行。
  • Priority:priority admission 會從 priorityClassName 算出 PodGroup 的 priority 與 preemptionPolicy;scheduler 要求 PodGroup 內每個 pod 的 priority 與 PodGroup 一致。

叢集需求(KubeRay 文件 docs/guidance/kubernetes-was.md):

  • apiserver --runtime-config=scheduling.k8s.io/v1beta1=true,scheduling.k8s.io/v1alpha3=true(KubeRay 用 v1alpha3,但 kube-scheduler 的 GenericWorkload 整合要 v1beta1 也被 serve)。
  • GenericWorkload=true:apiserver、controller-manager、scheduler。
  • (選用)PodGroupPreemptionPolicy=true:要用 Never 時才需要。

4. Operator 與 scheduler 怎麼分工

這跟 operator 有關嗎?它歸在 batch-scheduler 底下。

有關,它就是 operator 的程式碼。batchscheduler 是 ray-operator 裡的 package,和 RayCluster controller 跑在同一個 process,不是另外部署的元件。開關是 operator 的啟動參數(--feature-gates=KubernetesWAS=true),權限用的是 operator 的 ServiceAccount — 所以 #5266 讀 PriorityClass 的 RBAC 加在 kuberay-operator Helm chart 的 ClusterRole 上。

ray-operator/                          ← kuberay-operator binary
└── controllers/ray/
    ├── raycluster_controller.go       ← RayCluster reconciler
    ├── rayjob_controller.go
    └── batchscheduler/                ← 排程器整合 adapter(plugin)
        ├── interface/                 ← BatchScheduler 介面
        ├── schedulermanager.go        ← 依設定挑一個 plugin
        ├── volcano/  yunikorn/  kai-scheduler/  scheduler-plugins/
        └── kubernetes-was/v1alpha3/

batchscheduler 這個名字容易誤會:裡面的程式碼不做排程,只負責 (1) 依各排程器的格式建立物件(Volcano 的 PodGroup、WAS 的 Workload + PodGroup),(2) 在 pod 寫上 schedulerName、label 或 schedulingGroup。實際決策由外部排程器做:

plugin實際排程的是誰需要另外裝?
volcano / yunikorn / kai-scheduler各自的 scheduler要
scheduler-plugins裝了 coscheduling plugin 的 scheduler要
kubernetes-wasK8s 內建 default-scheduler不用,但要開 K8s feature gate

4.1 兩層契約:interface 不是給 scheduler 用的

這些 scheduler plugin interface 實際上怎麼被 scheduler 使用?

不會被任何 scheduler 呼叫。呼叫它們的只有 KubeRay operator 自己;operator 和 scheduler 之間沒有函式呼叫,只透過 API 上的物件溝通。

┌─────────────── kuberay-operator process ───────────────┐
│  RayCluster / RayJob controller                         │
│        │ 呼叫 Go interface(BatchScheduler)            │
│        ▼                                                │
│  batchscheduler plugin(volcano / kubernetes-was / ...)│
└────────┬────────────────────────────────────────────────┘
         │ create / update / delete K8s 物件
         ▼
   kube-apiserver:Workload、PodGroup、Pod(schedulerName、schedulingGroup)
         ▲
         │ watch
   kube-scheduler(或 Volcano、YuniKorn 等)
  • Go interface(batchscheduler/interface/):operator 內部的抽象,讓 controller 不用知道背後是哪個排程器。
  • K8s 物件:operator 與 scheduler 真正的契約。scheduler 只認 pod.spec.schedulerName、pod.spec.schedulingGroup、PodGroup 的 minCount / priorityClassName 等欄位,不知道 KubeRay 存在。

4.3 Reconcile 時:三個 hook 的呼叫點

4.4 容易混淆的名詞

名詞指的是
KubeRay 的 BatchScheduler interface、batchscheduler/*operator 內部的 adapter
KubeRay 的 batchscheduler/scheduler-plugins/其中一個 adapter,對接 kubernetes-sigs/scheduler-plugins 的 coscheduling
kube-scheduler 的 scheduling framework plugin(Filter、Score、PostFilter,例如 DefaultPreemption)跑在 scheduler process 裡的排程邏輯,跟 KubeRay 無關

5. 一次 RayCluster reconcile 會發生什麼

  1. 進 reconcilePods,先跑 DoBatchSchedulingOnSubmission

    raycluster_controller.go:993:每次 reconcile、在建立任何 pod 之前呼叫。回錯就整次 reconcile 中止並 requeue。

    錯誤即重試
    WAS 大量用「回 error 等下一輪」來排序刪除/重建

  2. 判斷要不要 gang

    was_v1alpha3.go:386 schedulingSkipReason:沒有 opt-in label,或 enableInTreeAutoscaling: true → 跳過,並呼叫 CleanupOnCompletion 把之前建的 Workload/PodGroup 刪掉。

    autoscaling 不支援
    minCount 會跟著 replicas 跳,目前直接放棄 gang

  3. sync Workload → sync PodGroup

    was_v1alpha3.go:114:先 buildSchedulingResources 算出期望狀態,再依序 syncWorkload(:125)、syncPodGroup(:175)。不存在就 create;存在但過期就刪掉等下一輪重建(見第 7 節)。

    PriorityClass lookup
    只發生在 create 分支(本 branch 新增)

  4. 建 pod 時掛上 gang

    raycluster_controller.go:1648 / 1671 / 1695(head、worker、multi-host worker)→ AddMetadataToChildResource(was_v1alpha3.go:70):設 schedulerName: default-scheduler,以及 spec.schedulingGroup.podGroupName = <cluster>-cluster。

    不分 group
    所有 pod 都指同一個 PodGroup

  5. kube-scheduler 做 all-or-nothing

    湊不滿 minCount 的話,所有 pod 一起留在 Pending。

    刪除 RayCluster
    靠 ownerReference GC 收掉 Workload/PodGroup

7. 叢集形狀改變時的處理

  • Workload 過期(isWorkloadStale,was_v1alpha3.go:398:template 數量/名稱或 minCount 不同):Workload 不可變,只能砍掉重建。順序是先刪 PodGroup(它引用 Workload)→ 回 error → 下一輪再刪 Workload → 回 error → 再下一輪重新 create 兩者。
  • PodGroup 過期(只比 gang.minCount):刪掉重建。
  • 刪 PodGroup 前先拔 finalizer(deletePodGroup,:216):否則還有 pod 引用時刪不掉,替換流程會卡住。
  • 刪除都帶 UID precondition(:381),避免誤刪同名的新物件。
  • 同名但不是自己 own 的物件:直接回錯,不跟別人搶(TODO:之後補 Warning event)。
  • Suspend:pod 刪掉但 Workload/PodGroup 保留,resume 時 pod 重新加入同一個 gang。
  • priority 欄位不參與 stale 判斷:建立後就固定,要換 PriorityClass 得重建 RayCluster(本 branch 文件已註明)。

8. 目前進行中:PriorityClass & preemption(#5266)

要解的問題:原本 Workload/PodGroup 不帶任何 priority,(1) 與 pod 的 priority 不一致,違反 scheduler 的要求;(2) 使用者無法讓整個 gang 以 Never 等待資源,只能用預設 PreemptLowerPriority 去搶。

做法:

  • buildSchedulingResources 把 head 的 priorityClassName / preemptionPolicy 寫進 template 與 PodGroup。
  • resolvePreemptionPolicy:policy 沒寫但有 class 時,create 前自己 GET PriorityClass 補上 policy(繞 upstream bug,見下節)。
  • 附帶:Helm priorityclass_role.yaml 與 kustomize overlay 加 cluster-scoped PriorityClass get/list/watch;kind 設定加 PodGroupPreemptionPolicy=true;docs、unit、e2e。

review 細節(gate 關閉時欄位被靜默 drop、globalDefault、gang 一致性驗證等)見 WAS PriorityClass & PreemptionPolicy。

9. Upstream bug 與修正

  1. API defaulting 先跑

    pkg/apis/scheduling/v1alpha3/defaults.go SetDefaults_PodGroup:gate 開且 preemptionPolicy 為 nil → 補成 PreemptLowerPriority。

    問題起點
    使用者沒填,卻被填了值

  2. priority admission 再比對

    plugin/pkg/admission/priority/admission.go admitPodGroup:從 PriorityClass 算出 Never,發現 spec 已有不同的值 → Forbidden。

    結果
    引用 Never class 又沒寫 policy 的 PodGroup 一律建不起來
  • upstream 修法(#143253,OPEN):移除 PodGroup(v1alpha3、v1beta1)與 CompositePodGroup(v1alpha3)的 preemptionPolicy defaulting,nil 留給 admission 依 PriorityClass 填,與 Pod 的流程一致;明確寫了衝突值仍會被拒。
  • KubeRay 何時能拿掉 workaround:修正 merge 且 KubeRay 支援的最低 K8s 版本都包含它之後(1.37 若沒 backport 就拿不掉)。可移除:resolvePreemptionPolicy 與兩個呼叫點、PriorityClass RBAC、文件中 lookup 相關限制。要保留:buildSchedulingResources 複製 class / 明確 policy 的邏輯。
  • Workload 不受此 bug 影響:upstream master 的 Workload 沒有 preemptionPolicy defaulting,priority admission 也不處理 Workload。所以 syncWorkload 裡的 lookup 是為了與 PodGroup 一致,不是 workaround。

10. 和 KAI Scheduler 的 gang scheduling 比較

這跟目前 KAI scheduler 的 gang scheduling 比有什麼差?

最大的差別在分工:KAI 是 KubeRay 只在 pod 上貼標籤,PodGroup 與排程都交給另外安裝的 KAI scheduler;WAS 是 KubeRay 自己建立 Workload + PodGroup,排程交給內建 kube-scheduler。

10.3 怎麼選

  • KAI:GPU 叢集、多團隊共用,需要 queue、配額、fair share 或 GPU 切分。KubeRay 端很薄,複雜度在 KAI 那側。
  • WAS:只要「整個 RayCluster all-or-nothing」,不想多裝、維運另一套 scheduler。代價是 alpha API、沒有 queue 與配額,KubeRay 要自己管 PodGroup 生命週期 — 這也是 WAS PR 會碰到 RBAC、finalizer、過期重建與 upstream defaulting bug 的原因。
  • 兩者在 KubeRay 只能擇一:ValidateBatchSchedulerConfig 會擋同時設定。
