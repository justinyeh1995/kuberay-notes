KubeRay PR #5210 · idle termination × GCS FT

Finalizer Reconcile Notes

整理自 2026-09-19 至 09-21 的問答 · 行號指修改前的 raycluster_controller.go

一句話:RayCluster 同時掛了 GCS FT 與 idle-termination 兩個 finalizer 時,GCS FT block 每一輪都提前 return,idle-termination finalizer 永遠輪不到,CR 卡在 Terminating。

  • 修法:把 idle-termination block 移到 GCS FT block 前面,外層條件加上「自己的 finalizer 還在」,移除 finalizer 之後不要 return,同一輪繼續往下走。
  • 不用動 GCS FT 的程式碼,改動只在 PR #5210 自己新增的 block。
  • 為什麼不能靠 Update 觸發下一輪:RayCluster 的 watch 有 predicate,只改 finalizer 的事件會被擋掉。

1. Bug 卡在哪

原本一直出不去,是停在 GCS FT block 的哪一段?

停在「Redis cleanup Job 已完成」的分支(第 305–333 行),每一輪都在第 332 行 return ctrl.Result{}, nil 結束:

第 248 行 guard 成立(只看 spec 有沒有設 gcsFaultToleranceOptions)
  → 第 263 行 else(DeletionTimestamp 已設)
  → 刪 Pod(已經沒有) → 列出 Job → hasGCSFTFinalizer 為 false
  → 第 305 行 Job 還在 → 第 310 行 IsJobFinished 為 true
  → 第 311-314 行 RemoveFinalizer(此時是 no-op)+ Update
  → 第 332 行 return    ← 第 356 行的 idle-termination block 到不了

關鍵是 guard 只看 spec,不看 GCSFaultToleranceRedisCleanupFinalizer 是否還在,所以自己的 finalizer 移除之後,同一個 block 還是會攔截。

所以會一直重建 cleanup Job 嗎?

不會。Job 沒有設 TTL(grep 不到 TTLSecondsAfterFinished),而且有 owner reference 指向 RayCluster(buildRedisCleanupJob 裡的 SetControllerReference),完成的 Job 會一直留著,第 305 行的 len(Items) != 0 一直成立,不會走到第 337 行的建立分支。

只有兩種情況會重建:完成的 Job 被手動刪掉;或用 foreground cascading deletion 刪 CR,GC 可能先清掉 Job(這一點沒驗證)。實驗時看 kubectl get jobs -w 或 events 裡 Created Redis cleanup Job 出現幾次即可確認。

2. 修法怎麼演進

想法結論原因
把 idle block 搬到 GCS block 前面 單獨不夠 idle block 的 return 在 if hasFinalizer 外面,只要「開啟且刪除中」就無條件 return;搬前面之後換成 GCS block 永遠跑不到,Redis cleanup 不會執行,GCS finalizer 卡住
搬前面 + 外層條件加 hasIdleTerminationCleanupFinalizer 可行 只有自己的 finalizer 還在時才攔截,移除後就放行
有 GCS finalizer 時 requeue 不需要,而且危險 idle finalizer 是稽核用途,不需要等 GCS。block 排在 GCS block 前面時,回傳 RequeueAfter 會讓 GCS block 一直跑不到
移除 finalizer 後 return ctrl.Result{}, nil 有缺口 沒有 RequeueAfter,而 Update 產生的事件會被 predicate 擋掉(見第 3 節),沒有東西叫醒下一輪
移除 finalizer 後不 return,同一輪往下走 採用 同一輪就進入 GCS block,它自己會 RequeueAfter 推進後面的流程
改 GCS FT block 的門檻(hasGCSFTFinalizer) 選配,可另開 PR 可行且對應 Argo CD 的結構,但要動既有的 Redis cleanup 刪除邏輯,review 範圍較大

最終的程式碼形狀

raycluster_controller.go · 位於 GCS FT block 之前

if utils.IsIdleTerminationOptionsEnabled(&instance.Spec) {
    if instance.DeletionTimestamp != nil && !instance.DeletionTimestamp.IsZero() {
        if r.hasIdleTerminationCleanupFinalizer(instance) {
            // log + DeletedIdleRayCluster event
            controllerutil.RemoveFinalizer(instance, utils.IdleTerminationCleanupFinalizer)
            if err := r.Update(ctx, instance); err != nil {
                return ctrl.Result{RequeueAfter: DefaultRequeueDuration}, err
            }
            // 不 return:同一輪繼續進 GCS FT block
        }
    }
}
// ... enableGCSFTRedisCleanup、stale embedded finalizer、GCS FT block ...

兩個 finalizer 都在時的流程

同一輪:idle block 移除 idle finalizer → Update
        → 往下進 GCS block:刪 Pod,head Pod 還在 → RequeueAfter 10 秒
之後:   idle block 被跳過(finalizer 已不在)
        → GCS block 等 Pod 結束 → 建 Redis cleanup Job → 等 Job 完成
        → 移除 GCS finalizer → CR 被刪除

如果沒開 GCS FT 會怎樣?

idle block 移除 finalizer 並 Update,沒有其他 finalizer 的話 CR 這時就被刪除了。接著往下走:stale embedded block 條件不成立,GCS FT block 跳過,最後停在 generic fallback(RayCluster is being deleted, just ignore,return ctrl.Result{}, nil)。結果和原本一樣,只多一行 log。ENABLE_GCS_FT_REDIS_CLEANUP=false 也是同一條路徑。

3. Predicate 與 Reconcile 觸發

predicate 是什麼?

controller-runtime 裡的事件過濾器,決定一個資源事件要不要觸發 Reconcile:

API server 上的資源變動
  → watch 收到事件(Create / Update / Delete)
  → predicate 判斷:要不要處理?
  → 通過才放進 workqueue
  → Reconcile() 被呼叫

用途是避免不相關的變動(例如 controller 自己寫的 status)一直觸發自己。

KubeRay 的 RayCluster 怎麼設?

raycluster_controller.go · SetupWithManager

For(&rayv1.RayCluster{}, builder.WithPredicates(predicate.Or(
    predicate.GenerationChangedPredicate{},  // spec 變了
    predicate.LabelChangedPredicate{},       // labels 變了
    predicate.AnnotationChangedPredicate{},  // annotations 變了
)))

Update 事件帶有舊、新兩份物件,predicate 比較兩者;Or 表示任一個成立就放行。generation 是 apiserver 在 spec 變更時遞增的計數器,改 status 或 metadata 不會遞增。

所以移除 finalizer 的 Update 大概不會觸發下一輪。它只改 metadata.finalizers,三個條件都不成立,事件被丟掉。這是根據 Kubernetes 的一般行為與這段 predicate 推論的,沒有在實際叢集上驗證。

會觸發 Reconcile不會(被擋掉)
spec 變更、labels 或 annotations 變更 只改 metadata.finalizers、只改 status
Owns(Pod / Service / Secret / PVC) 的事件(另外的 watch,沒套這個 predicate) —
Reconcile 自己回傳的 RequeueAfter(直接進 workqueue,不經過 predicate) —

那為什麼要拿掉 Update 之後的 return?

保留 return:  移除 finalizer → return(不排下一輪)
              → Update 的事件被 predicate 擋掉
              → 沒人叫醒 Reconcile,GCS cleanup 要等別的事件才開始

拿掉 return:  移除 finalizer → 繼續往下
              → 同一輪進 GCS block,它自己會 RequeueAfter 推進

拿掉 return 是讓 idle block 做完事之後,在同一輪把接力棒交給 GCS block,不必依賴一個不一定會來的事件。回傳 RequeueAfter: DefaultRequeueDuration 也是等價作法,只是多繞一輪。

前面另一個說錯又更正的地方

「no-op Update 不會產生 watch 事件」與「移除 finalizer 的 Update 會觸發下一輪」這兩句,前者只是推論,後者在這個 predicate 下是錯的。更精確的說法:每一輪停在第 332 行沒有 RequeueAfter,所以是「該輪結束,等別的事件」,不是持續空轉。

4. 業界怎麼做(摘要)

  • Argo CD 的 finalizeApplicationDeletion 是唯一通過「同一物件、多個 finalizer、同一個函式處理」篩選的例子:每個 block 以自己的 finalizer 為門檻,只有在等待中,或剛移除自己的 finalizer 時才 return。門檻原則與這次修法相同。
  • Cluster API、KubeVirt、Crossplane 多半是一個 reconciler 一個 finalizer;Kueue、Rook 每個物件只有一個 finalizer。沒有專案靠 block 順序避免互相餓死。
  • Kubernetes 規則:deletionTimestamp 設定後只能移除 finalizer,不能新增。
  • 完整的來源與查證程度見 Artifact「Finalizer Prior Art」(連結,私人)。
