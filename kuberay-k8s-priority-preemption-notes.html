PriorityClass 與 Preemption

整理自 2026-10-22 的問答 · 起因:review KubeRay #5422 時對 preemptionPolicy: Never 的疑問 · 相關筆記:Kubernetes WAS Overview、WAS PriorityClass & PreemptionPolicy、Gang Scheduling Mechanics、Apiserver Admission Flow

三句話:

  • Preemption 只發生在 kube-scheduler 排程時:一個 Pending 的 pod(或 gang)排不進去,scheduler 才考慮驅逐別人。
  • preemptionPolicy 管的是「我會不會去搶別人」,不是「別人能不能搶我」。Never 的 pod 照樣會被更高 priority 的 pod 搶。
  • WAS 的 Never 會被拒絕是 upstream bug(PodGroup 多做了一個 Pod 沒有的預設值),不是 Never 不能用。

1. scheduling.k8s.io 裡有什麼

這個 API group 的資源主要都是給 kube-scheduler 用的。

資源誰用、怎麼用
PriorityClass(v1,cluster-scoped)priority admission 在建立 pod 時,把 value 寫進 pod.spec.priority、把 preemptionPolicy 寫進 pod;scheduler 再拿來排序與做 preemption
Workload / PodGroup(v1alpha3,K8s 1.37)kube-scheduler 以 PodGroup 為單位做 gang 決策(湊滿 minCount 才放行)

2. Preemption 什麼時候發生

  1. pod 是 Pending,scheduler 嘗試排它

    依 priority 從排程佇列取出,高的先排。

    priority 的第一個作用
    決定排隊順序

  2. Filter 找不到放得下的節點

    所有節點都因資源或約束不符被濾掉。

    放得下就不會 preempt
    直接 bind

  3. 進入 PostFilter:DefaultPreemption plugin

    這時才讀這個待排 pod 自己的 preemptionPolicy:Never → 不搶,回佇列等;PreemptLowerPriority → 挑 priority 比它低的 victim 驅逐,騰出位置。

    唯一讀 preemptionPolicy 的時刻
    pod 跑起來之後這個欄位就沒作用了

所以「被搶」是因為別的 Pending pod 進了 PostFilter,挑中你當 victim;跟你自己的 preemptionPolicy 無關。

3. Never 到底是什麼意思

priority class: Never 那沒有人可以 preempt 他們?

不是,方向剛好相反。Never 就是 non-preempting priority(K8s 1.24 GA):在排隊時享有高 priority,但不會為了自己去踢人。

行為PreemptLowerPriority(預設)Never
排程佇列中照 priority 排順序✅✅
資源不夠時,驅逐比它低的 pod✅❌ 只會等
被比它高、且可搶佔的 pod 驅逐會一樣會
kubelet node-pressure eviction會(參考 priority)一樣會(不看 preemptionPolicy)

例子:Ray 叢集用 value: 1000, preemptionPolicy: Never

  • 來一個 value: 500 的 pod、資源不夠 → Ray 叢集不會踢它,自己排隊等。
  • 來一個 value: 2000、policy 預設的 pod、資源不夠 → Ray 的 pod 照樣被驅逐。

想要「不被搶」要靠別的機制

  • priority 調高:比你高的工作少,被搶的機會就少(system-cluster-critical 這類數值很高的 class 不該給一般工作用)。
  • PodDisruptionBudget:scheduler preemption 只是盡量遵守、不保證;PDB 主要擋 drain 這類自願驅逐。
  • 切開資源:taint/toleration、獨立 node pool、ResourceQuota。

4. priority 在 scheduling 以外的用途

  • kubelet node-pressure eviction:記憶體/磁碟不足時,kubelet 參考 priority 決定先驅逐誰,完全不看 preemptionPolicy。
  • ResourceQuota:可用 scopeSelector 依 PriorityClass 分開設額度。

5. 放到 WAS:PodGroup 的 preemptionPolicy

K8s 1.37 的 PodGroupPreemptionPolicy gate 把同一個概念延伸到 gang:scheduler 為整個 PodGroup 湊 minCount 湊不滿時,才決定要不要搶。Never = 整組一起等,不踢人。

  • scheduler 以整組為單位排序與做 preemption,所以要求 PodGroup 與其每個 pod 的 priority 一致。KubeRay 因此必須讓 head 與所有 worker group 用同一個 PriorityClass。
  • policy 有兩個來源:PodGroup 的 spec.preemptionPolicy 與 PriorityClass 的 preemptionPolicy。priority admission 以 class 為準,PodGroup 上若有值就必須一致。

未查證:gang 中有 pod 被搶之後,整組怎麼處理(PodGroup 的 disruptionMode 與 1.37 的 gang preemption 行為)還沒讀 upstream 程式碼確認。

6. 為什麼 WAS 的 Never 會被拒絕

「Kubernetes defaults an unset PodGroup preemptionPolicy before admission, rejecting Never」那為什麼還要有 Never 這個選項?

Never 是正式選項;被拒絕是 upstream bug,而且只在一種組合發生。API defaulting(SetDefaults_PodGroup)比 priority admission 先跑:

PodGroup spec.preemptionPolicyPriorityClass結果
明確寫 NeverNever✅ 通過
沒寫PreemptLowerPriority 或沒設✅ 被補成 PreemptLowerPriority,剛好一致
沒寫Never❌ defaulting 先補成 PreemptLowerPriority → admission 判定與 class 衝突 → Forbidden
  • Pod 沒有這個問題:Pod 的 preemptionPolicy 沒有 API defaulting,留空由 admission 從 PriorityClass 補上。PodGroup 加欄位時多做了一個 Pod 沒有的預設值。
  • upstream 修正:kubernetes#143252 / #143253(OPEN),拿掉 PodGroup / CompositePodGroup 的 preemptionPolicy defaulting,"matching the Pod admission flow"。
  • KubeRay 的 workaround(resolvePreemptionPolicy):create 前自己讀 PriorityClass,把 policy 明確寫成 Never,落在表格第一列。

建議把 KubeRay 那句容易誤讀的註解改成

// Kubernetes 1.37 defaults an unset PodGroup preemptionPolicy to PreemptLowerPriority
// before priority admission runs, so a PriorityClass with preemptionPolicy: Never is
// rejected as a mismatch. Set the policy from the class explicitly to avoid that.
// See https://github.com/kubernetes/kubernetes/issues/143252
