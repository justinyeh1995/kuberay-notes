Operator RBAC:marker、Kustomize 與 Helm

整理自 2026-10-22 的問答 · 起因:KubeRay #5266 同時改了 Helm chart 與 kustomize overlay 的 RBAC · 相關筆記:Kubernetes WAS Overview、WAS PriorityClass & PreemptionPolicy

重點:operator 對 API 的每個操作(包括 reconciler 的 GET)都以 kuberay-operator 的 ServiceAccount 身分執行,需要 RBAC 授權。權限有三種來源:

  • 一般權限:controller 上的 +kubebuilder:rbac marker → controller-gen 產生 config/rbac/role.yaml;Helm 再手抄一份。
  • 選用功能的權限(例如 WAS):不能用 marker,在 Kustomize overlay 與 Helm 條件區塊各寫一次。
  • cluster-scoped 又是選用的權限(例如 PriorityClass):Helm 還得獨立成 ClusterRole。

1. 一般權限:kubebuilder RBAC marker

原本 operator 常用的 reconciler GET 權限是在哪裡設定的?

寫在 controller 程式碼的註解裡,例如 ray-operator/controllers/ray/raycluster_controller.go:91-102:

// +kubebuilder:rbac:groups=ray.io,resources=rayclusters,verbs=get;list;watch;create;update;patch;delete
// +kubebuilder:rbac:groups=core,resources=pods,verbs=get;list;watch;create;update;patch;delete;deletecollection
// +kubebuilder:rbac:groups=core,resources=services,verbs=get;list;watch;create;update;patch;delete

rayservice_controller.go、networkpolicy_controller.go、raycluster_mtls_controller.go 也各有一組。

  1. controller 上寫 marker

    宣告這個 reconciler 需要哪些 group / resource / verb。

    就是註解
    不影響編譯

  2. make manifests

    ray-operator/Makefile:45:controller-gen rbac:roleName=kuberay-operator ... paths="./..." 掃描所有 marker、合併後輸出 ray-operator/config/rbac/role.yaml(ClusterRole kuberay-operator)。

Helm chart(helm-chart/kuberay-operator/)Kustomize(ray-operator/config/)
給誰用使用者正式安裝開發者與 CI:make deploy、make deploy-kubernetes-was-v1alpha3(Makefile:175)、Buildkite e2e
怎麼產生 YAMLGo template 依 values.yaml 渲染base YAML + overlay 的 patch

我在 repo 裡沒找到比對 Helm 規則與 config/rbac/role.yaml 的 CI 或腳本;看起來兩邊靠人工同步。改權限時兩邊都要改。

3. 選用功能為什麼不能用 marker

如果在 WAS 程式碼加上:

// +kubebuilder:rbac:groups=scheduling.k8s.io,resources=priorityclasses,verbs=get;list;watch

controller-gen 會把它產生進 base 的 config/rbac/role.yaml,每個安裝都拿到,不論有沒有開 WAS。marker 無法表達「只有開 feature gate 才給」。所以 WAS 的權限都放在有條件的位置:

Workload / PodGroupPriorityClass(#5266)
KustomizeWAS overlay 的 JSON patch,加到 ClusterRole kuberay-operator 的 /rules/-同一個 overlay 多一條 patch
Helmrole.consistentRules 的 {{- if .kubernetesWASEnabled }} 區塊(_helpers.tpl:425)獨立檔 templates/priorityclass_role.yaml(見第 4 節)

overlay 的註解寫明 "mirroring the Helm chart, which gates it on the KubernetesWAS feature gate",兩份同樣是手動同步。

4. 案例:#5266 的 PriorityClass 權限

Helm chart 跟 kustomize overlay 都有寫到 RBAC,是為啥?加上誰的權限?

兩邊加的是同一份權限:讓 kuberay-operator 的 ServiceAccount 能讀 PriorityClass。

  • 為什麼要:resolvePreemptionPolicy 呼叫 k.cli.Get(..., &PriorityClass{}),用的是 operator 的 client。沒有授權會回 403 Forbidden,PodGroup 建不起來。
  • 只給讀取:get / list / watch。要 list / watch 是因為 controller-runtime 的 client 預設走 informer cache,讀一個物件也要能 list、watch 該型別。
  • 只在開 WAS 時給:Helm 要 rbacEnable 且 KubernetesWAS gate 開啟;Kustomize 只有用 WAS overlay 部署時。

4.1 Helm 為什麼要另外寫一個 ClusterRole

singleNamespaceInstall: true(operator 只管單一 namespace)時,role.consistentRules 會被渲染成 namespaced Role。但 PriorityClass 是 cluster-scoped 資源,namespaced Role 無法授權,必須用 ClusterRole + ClusterRoleBinding。所以 PR 另外寫 priorityclass_role.yaml,不論是否單一 namespace 都渲染成 ClusterRole(檔案開頭註解與 tests/priorityclass_role_test.yaml 第 4 個 case 講的就是這件事)。

ClusterRoleBinding 綁的就是 operator 的 ServiceAccount

subjects:
- kind: ServiceAccount
  name: {{ include "kuberay-operator.serviceAccount.name" . }}
  namespace: {{ .Release.Namespace }}

4.2 review 時可以留意

  • 單一 namespace 安裝的權限範圍:開 WAS 後會多一個 cluster 層級的 ClusterRole。只能讀 PriorityClass,風險很低,但在單一 namespace 安裝下少見,release note 或文件最好提一句(PR 的 Limitations 寫了需要 cluster-scoped 權限,但沒特別點出 singleNamespaceInstall)。
  • workaround 移除時:upstream(kubernetes#143252)修好、拿掉 resolvePreemptionPolicy 後,兩份 RBAC 也要一起刪,Helm 那份連同 tests/priorityclass_role_test.yaml。
