KubeRay issue #5364 · worker group reconciliation

Worker Group Deadlock Notes

整理自 2026-10-04 的問答 · issue #5364 · branch fix/issue-5364-worker-group-deadlock · 相關筆記:Pod Create vs Schedule

一句話:reconcilePods 依固定順序逐一處理 worker group,任何一個 group 建立 Pod 失敗就直接 return,整個迴圈結束。namespace quota 滿了的時候,排在前面的 group 每一輪都失敗,排在後面的 group 永遠輪不到刪除 WorkersToDelete,而那些 Pod 正是佔住 quota 的元兇。

  • 修法:建立失敗時把錯誤收集起來(errors.Join)、break 跳出該 group 的建立迴圈、繼續下一個 group,迴圈結束後再回傳。
  • 範圍:只處理「建立 Pod 失敗」這一類錯誤,包含 L1202、L1210、multi-host 的 L1418 → L1098 三條路徑。
  • 測試:TestReconcile_CreateFailureDoesNotBlockOtherWorkerGroups 已寫好,目前如預期失敗。

1. 從 L1210 開始追:為什麼會卡死

L1210 做了什麼?

worker 迴圈從 raycluster_controller.go:1069 開始,依 Spec.WorkerGroupSpecs 的順序跑。每個 group 先刪 WorkersToDelete(L1135),再建立缺少的 Pod(L1182)。建立失敗時:

for i := range diff {
    if err := r.createWorkerPod(ctx, *instance, *worker.DeepCopy()); err != nil {
        return errstd.Join(utils.ErrFailedCreateWorkerPod, err)   // L1210
    }
}

這個 return 離開的是整個 reconcilePods,不只是這個 group。

卡死的過程

  1. Group A(排前面)diff > 0,建立 Pod 被 quota 拒絕,L1210 return。
  2. 錯誤傳回 Reconcile(L373),停止後續 reconcile 函式、寫入 ReplicaFailure status、requeue。
  3. 下一輪順序一樣、quota 還是滿的,group A 又失敗。Group B 永遠到不了自己的 WorkersToDelete。

卡死需要兩個條件同時成立:順序固定,而且錯誤不會自己消失。錯誤不會消失,是因為 group B 刪不掉的 Pod 就是佔住 quota 的那些。

只有失敗的 group 排在有待刪 Pod 的 group 前面時才會發生。把 spec 裡的順序對調就重現不出來,寫測試時要注意。

用數字走一遍:group A 沒被建立?group B 有被建立?

group 本身沒有「建立」這回事,它只是 spec 裡的一筆設定,A 和 B 一直都在。會被建立或刪除的是 group 底下的 Pod。issue 的 Group 1 就是 group A,Group 2 就是 group B。假設 namespace 的 ResourceQuota 是 pods: "10"(先不算 head):

ASD-STE100 版本

ASD-STE100 是以英文為基礎的受控語言:短句、一句只講一件事、主動語態。

The problem

  1. The cluster has two worker groups: group A and group B.
  2. The namespace quota is 10 Pods. The two groups use the same quota.
  3. Group A has 6 Pods. Group A must have 8 Pods.
  4. Group B has 4 Pods. Group B must have 1 Pod.
  5. The autoscaler writes the names of 3 Pods of group B in workersToDelete.
  6. The controller must delete these 3 Pods. The autoscaler does not delete Pods.
  7. The quota is full. Thus, the controller cannot create Pods for group A.

What the controller does now

  1. The controller always does group A first and group B second.
  2. The controller tries to create a Pod for group A.
  3. The quota is full. Thus, Kubernetes rejects the Pod.
  4. The controller stops all work for the cluster. It does not go to group B.
  5. The 3 Pods of group B stay. They use 3 places in the quota.
  6. The controller tries again later. The same steps occur again.
  7. Result: the controller cannot create Pods for group A. It also cannot delete Pods of group B.

What the controller does after the fix

  1. The controller tries to create a Pod for group A.
  2. Kubernetes rejects the Pod.
  3. The controller keeps the error. It stops work for group A only.
  4. The controller goes to group B. It deletes the 3 Pods.
  5. Now the quota has 3 empty places.
  6. The deletion of the Pods starts a new pass of the controller.
  7. In the new pass, the controller creates 2 Pods for group A.
  8. Result: group A has 8 Pods. Group B has 1 Pod.

所以 group A、group B 有順序性?

對,順序就是 spec.workerGroupSpecs 陣列裡的順序。L1069 是 for _, worker := range instance.Spec.WorkerGroupSpecs,每一輪都是第 0 個先、第 1 個後,永遠一樣。

  • 失敗的 group 排前面(A 在 B 前):每一輪都在 A 那裡 return,B 永遠跑不到,卡死。
  • 順序反過來(B 在 A 前):B 先刪掉 workersToDelete 的 Pod,quota 空出來;接著 A 失敗、return,但 B 已經刪完了。下一輪 A 就建得起來,不會卡死。

同一個 cluster,只要在 YAML 裡把兩個 group 對調,這個 bug 就會消失。測試裡刻意寫成 []rayv1.WorkerGroupSpec{groupA, groupB},順序寫反的話,測試在修之前就會通過,也就測不到 bug。修好之後順序就不重要了,失敗只會停掉自己那個 group。

namespace quota 是 ResourceQuota?還是 spec.resources.limits?

是 ResourceQuota。它和 Pod 的 resources.limits 是不同層級,但兩者有關:

設定是什麼範圍寫在哪
ResourceQuotanamespace 的總額度整個 namespace 加總獨立物件 kind: ResourceQuota
resources.limits / requests單一 container 的用量一個 containerPod spec 裡
LimitRange單一 container 的預設值與上下限每個 container 各自檢查獨立物件 kind: LimitRange
 
apiVersion: v1
kind: ResourceQuota
metadata:
  name: pod-quota
  namespace: ray
spec:
  hard:
    pods: "10"              # Pod 數量上限
    requests.cpu: "20"      # 所有 Pod 的 CPU request 加總上限
    requests.memory: 64Gi
    limits.cpu: "40"        # 所有 Pod 的 CPU limit 加總上限
    limits.memory: 128Gi

ResourceQuota 算的就是每個 Pod 的 requests / limits 的加總。例如每個 worker 都是 limits.cpu = 4,10 個 Pod 就是 40 CPU,剛好把 limits.cpu 用滿。issue 說的 pod 數、CPU、記憶體三種情況是同一種機制,只差 spec.hard 哪一項先用完。

建 Pod 時 apiserver 的 ResourceQuota admission 檢查加上這個 Pod 會不會超額,超過就直接回 403 Forbidden,Pod 根本不會被建立:

pods "raycluster-group-a-xxxxx" is forbidden: exceeded quota: pod-quota,
requested: pods=1, used: pods=10, limited: pods=10

測試 interceptor 回傳的 k8serrors.NewForbidden(... "exceeded quota" ...) 模擬的就是這個。

  • quota 有 CPU/記憶體項目時,Pod 一定要寫 requests/limits,否則也會被拒(must specify limits.cpu),除非有 LimitRange 補預設值。重現環境時可能會踩到。

未確認:印象中 quota 的 Pod evaluator 會排除 Succeeded/Failed 的 Pod,而 graceful termination 中的 Pod 要過了 grace period 才不算,還沒去翻 k8s 原始碼確認。如果是這樣,修好之後 B 送出刪除的下一輪,A 可能還是被拒;等 B 的 Pod 真的消失又產生 Pod event,再一輪 A 才建成功。會多失敗一兩輪,但最後仍會自己恢復,結論不變。

也就是回報者的 cluster 有 ResourceQuota 這個物件?

很可能有,但 issue 沒有直接證據:沒貼 YAML,只寫「resource namespace quota error」和「Set k8s resource limits to something relatively low」。不過可以反推,因為 bug 要發生,建 Pod 時必須直接收到錯誤,只有 admission 階段被拒才會這樣:

情況Pod 會怎樣createWorkerPod觸發 bug?
ResourceQuota 用滿不會被建立收到 403 exceeded quota會
node 資源不夠(CPU、記憶體、EKS 每台 node 的 max pods)建立成功,卡在 Pending成功,沒有錯誤不會

node 資源不夠時,Pending 的 Pod 也會算進 runningPods(L1154 只排除剛刪掉的 Pod,不看 phase),diff 變成 0,controller 正常跑到 group B,不會卡住。為什麼建立和排程是分開的,見 Pod Create vs Schedule。

  • 他說的是「quota error」,描述的現象也是 reconcile 被中斷,只符合第一種。EKS 多租戶 cluster 由 platform 團隊在每個 namespace 放 ResourceQuota 很常見,使用者自己不一定知道。
  • 其他會在 admission 階段拒絕 Pod 的東西也會觸發同一個 bug,例如 OPA Gatekeeper、Kyverno 這類 policy webhook。修法不看錯誤種類,只要建立失敗就繼續下一個 group,所以一樣適用。可以寫進 PR 描述。
  • 想確認的話,可以請回報者貼 kubectl get resourcequota -n <ns> -o yaml 和 controller log 裡的錯誤訊息,但修法不需要等這個答案。

沒有 ResourceQuota 的話,一般 autoscaling 就不會遇到問題嗎?

大部分情況不會,但「沒有 ResourceQuota」不等於「安全」。關鍵是:建 Pod 時有沒有直接收到錯誤,而且這個錯誤會不會一直重複。

一般的 autoscaling 資源不夠,通常是 node 不夠:autoscaler 調高 replicas → KubeRay 建 Pod 成功 → Pod 卡在 Pending,等 Cluster Autoscaler 或 Karpenter 加 node → KubeRay 繼續處理 group B。Pending 的 Pod 算進 runningPods,diff 是 0,不會卡住。這是最常見的情況。

沒有 ResourceQuota 也會觸發的情況:任何會讓 apiserver 在建立時一直拒絕某個 group 的 Pod 的東西:

原因例子
policy webhookOPA Gatekeeper、Kyverno 的規則擋下 group A 的 Pod(例如禁止某個 image registry)
Pod Security Admissionnamespace 設成 restricted,group A 的 Pod 要求 privileged
LimitRangegroup A 的 container 要的資源超過 LimitRange 的 max
Pod spec 不合法apiserver 驗證失敗回 422(例如 requests 大於 limits),而 KubeRay 自己的 validation 沒抓到

這些和 quota 有一個重要差別:從一開始就失敗,不用等到 burst。group A 只要設定錯了,排在後面的 group B 就完全不會被 reconcile,不只刪不掉 Pod,連擴容都不會發生。

  • 影響範圍比 issue 描述的大:真正的問題是「一個 group 的持續性建立失敗會擋住其他所有 group」,修法同時讓各 group 彼此隔離。
  • 修法不用改:它不看錯誤種類,只要建立失敗就記下來、繼續下一個 group。
  • 暫時性錯誤本來就沒問題:API server 抖一下、網路斷一下,下一輪 reconcile 就恢復。

上面的表是從 apiserver 的 admission 機制推出來的,沒有一個一個實測。PR 描述用「for example, admission webhooks or Pod Security Admission」這種舉例寫法,不要寫成已驗證的事實。

2. L1210 不是唯一的出口

迴圈裡還有哪些地方會提早 return?

同樣的「在單一 group 裡 return」共有 9 處,另外 reconcileMultiHostWorkerGroup 裡還有 L1418:

行號情境性質
L1080List Pod 失敗整個 cluster 層級,停下來是對的
L1088suspended group 刪 Pod 失敗刪除失敗
L1098reconcileMultiHostWorkerGroup 回傳錯誤(含 L1418 建立失敗)建立失敗,要修
L1118刪除 unhealthy Pod 失敗刪除失敗
L1129刪除 unhealthy Pod 成功 後也 return刻意設計,下一輪會自己好
L1144刪除 WorkersToDelete 失敗刪除失敗
L1188mTLS secret 還沒準備好整個 cluster 層級,停下來是對的
L1202建立 Pod 失敗(RayMultiHostIndexing 開啟)建立失敗,要修
L1210建立 Pod 失敗(gate 關閉)建立失敗,要修
L1245隨機刪除 Pod 失敗刪除失敗

現有程式碼的隱含假設是「任何一個 group 出錯都代表整個 cluster 有問題,所以整輪停下來」。這對 List 和 mTLS 成立,對 quota 拒絕這種單一 group 的錯誤不成立。

改成收集錯誤,status 會不會壞掉?

不會。RayClusterReplicaFailureReason(utils/constant.go:437)用的是 errors.As,對 errors.Join 包起來的多個錯誤也有效,會回報第一個錯誤的 reason。

3. 要修整個問題,還是只修 issue 的範圍?

issue 有明確範圍,要全部修嗎?

結論:照 issue 的範圍修,但範圍定義成「一個 group 建立 Pod 失敗,不應該擋住其他 group」。這比只修 L1210 多一點,但不是 9 個出口全修。

位置決定理由
L1210修issue 指的那一行
L1202修同樣的建立,只是走 RayMultiHostIndexing 分支;而且這個 gate 預設開啟(見第 4 節)
L1418 → L1098修multi-host group 的建立,同樣被 quota 拒絕、同樣卡死
刪除失敗(L1088/1118/1144/1245)不修,寫在 PR 描述quota 不會擋刪除;webhook 或 RBAC 問題理論上會,但沒有回報過、是另一個 issue
L1129不修刻意的;下一輪該 group 的 expectation 未滿足,L1070 會跳過它,其他 group 照常跑
L1080、L1188不修真的是整個 cluster 層級

為什麼不全修:KubeRay maintainer 通常比較快合併聚焦的 PR。改變所有錯誤路徑的行為,需要另外討論「哪些錯誤應該停下整輪」。刪除失敗的情況可以在這個 PR 合併後另開 follow-up issue,跟 #5210 一樣的做法。

4. RayMultiHostIndexing 是什麼

這個 feature gate 做什麼?

定義在 pkg/features/features.go:35,替 worker Pod 加上穩定的 index label:

  • ray.io/worker-group-replica-index:這個 Pod 屬於 group 裡第幾個 replica(0 到 replicas-1)。
  • ray.io/worker-group-replica-name、ray.io/replica-host-index:一個 replica 由多個 Pod 組成時(NumOfHosts > 1),用來把同一個 replica 的所有 host 當成一個單位管理。

所以迴圈裡有三條建立路徑:

條件路徑建立失敗的位置
gate 開、NumOfHosts > 1整個 group 交給 reconcileMultiHostWorkerGroup(L1096)L1418,錯誤從 L1098 出來
gate 開、NumOfHosts == 1一般 group,但新 Pod 拿最小的空 replica index(L1191–1204)L1202
gate 關一般建立(L1206–1212)L1210

這個 gate 預設是 true(Beta,features.go:124)。所以回報者在預設安裝的 1.7.1 上,single-host group 很可能走的是 L1202,不是 L1210。issue 連結的是看起來最明顯的那一行,實際跑的可能是另一行。只修 L1210 很可能修不到回報者的 bug。

修法真的只有幾行嗎?

對,大概是這樣:

var errs []error
for _, worker := range instance.Spec.WorkerGroupSpecs {
    ...
    if isRayMultiHostIndexing {
        if err := r.reconcileMultiHostWorkerGroup(...); err != nil {
            if !errstd.Is(err, utils.ErrFailedCreateWorkerPod) { return err }
            errs = append(errs, err)
        }
        continue
    }
    ...
    for i := range diff {
        if err := r.createWorkerPod(...); err != nil {
            errs = append(errs, errstd.Join(utils.ErrFailedCreateWorkerPod, err))
            break // stop creating for this group, move on to the next
        }
    }
    ...
}
return errstd.Join(errs...) // nil if errs is empty
  • 內層用 break 不是 continue:一個建立被 quota 拒絕,剩下的也會被拒。每輪重試 diff 次只會灌爆 API server 和 event。
  • L1098 的 errstd.Is:只讓 multi-host 路徑的建立失敗繼續往下,其他錯誤(例如刪除失敗)維持現在整輪停下的行為。
  • diff > 0 分支是迴圈主體的最後一段,break 出來就會接到下一個 group。

這段建立迴圈的語意是什麼?

「這個 group 建 Pod 失敗了,記下錯誤,不要再試這個 group,接著處理下一個 group。」

  • for i := range diff:Go 1.22 起可以對整數 range,i 從 0 跑到 diff-1,缺幾個 Pod 就建幾次。
  • if err := ...; err != nil:if 帶初始化敘述,err 只在這個 if 裡有效。
  • errstd.Join(utils.ErrFailedCreateWorkerPod, err):把真正的原因(例如 Forbidden: exceeded quota)和 KubeRay 的標記包成一個錯誤。calculateStatus 靠這個標記把 ReplicaFailure 的 reason 寫成 FailedCreateWorkerPod。原本的 L1210 就是這樣包的,差別只在不 return,改成 append 進 errs。
  • return errstd.Join(errs...):errs 是空的話回傳 nil。
寫法離開哪裡結果
return(現在的 L1210)整個 reconcilePods後面的 group 都跑不到,就是這個 bug
continue只跳過內層這一圈繼續建下一個 Pod,quota 滿的話每個都被拒,白打 API server
break只離開內層建 Pod 的迴圈不再建這個 group 的 Pod,接著跑外層下一個 group

errors.Is 是什麼?

errors.Is(err, target) 問的是「這個錯誤裡面有沒有包著 target」。看 $GOROOT/src/errors/wrap.go:

  1. err == target 就回 true。
  2. 不是就 Unwrap() 拆一層再比,一直拆到底。
  3. 遇到 Join 產生的錯誤(Unwrap() []error),裡面每一個都去比。

所以包好之後 errors.Is(joined, utils.ErrFailedCreateWorkerPod) 是 true,測試裡的 require.ErrorIs 就是用這個。相近的 errors.As 問的是「裡面有沒有這個型別,有就拿出來」,RayClusterReplicaFailureReason 用的是 As。

命名陷阱:raycluster_controller.go 裡的 errors 是 k8s 的 apimachinery/pkg/api/errors(L1141 的 errors.IsNotFound),標準庫 errors 改名成 errstd(L7)。所以 L1098 要寫 errstd.Is,不是 errors.Is。

延伸閱讀:Go blog〈Working with Errors in Go 1.13〉、pkg.go.dev/errors、$GOROOT/src/errors/wrap.go 與 join.go。

這樣不就每一個 err 的地方都要收集?

不用。只有決定要改的 3 個地方收集,其他 return 不動:

位置改法
L1202、L1210(建立失敗)append 進 errs + break
L1098(multi-host)errstd.Is 判斷:建立失敗就 append + continue,其他錯誤照樣 return
其他 7 個 return不動,一樣馬上結束整個函式
迴圈結束後return errstd.Join(errs...)

函式裡會同時有兩種處理:建立失敗「記下來,繼續跑」,其他錯誤「馬上停」。這就是第 3 節範圍決定在程式碼上的樣子。

混用有什麼副作用?

Group A 建立失敗、錯誤存進 errs;接著 group B 刪除失敗,return errstd.Join(ErrFailedDeleteWorkerPod, err)。這個 return 只帶 group B 的錯誤,group A 已收集的錯誤被丟掉。

  • requeue 不受影響:回傳的錯誤還是非 nil。
  • status reason 寫 FailedDeleteWorkerPod 而不是 FailedCreateWorkerPod。一個 condition 本來就只放一個 reason,收集了也只顯示第一個。
  • group A 的失敗還是有紀錄:createWorkerPod 失敗時先發 FailedToCreateWorkerPod event(L1703)才回傳,kubectl describe 看得到。

結論:可以接受,不為此改另外 7 個 return。真的不想丟錯誤有兩種做法,但都比較重:

  • 每個 return 改成 return errstd.Join(append(errs, err)...):diff 變大、容易漏改。
  • 把迴圈主體抽成 reconcileWorkerGroup(...),外層統一處理錯誤:diff 最大,reviewer 要看懂的最多。

5. reconcile 怎麼被觸發

有些 r.Update 不會觸發 reconcile,修好之後 loop 怎麼知道要再跑?

先看 SetupWithManager(raycluster_controller.go:1937):

For(&rayv1.RayCluster{}, predicate.Or(
    GenerationChangedPredicate{},  // spec changes
    LabelChangedPredicate{},
    AnnotationChangedPredicate{})).
Owns(&corev1.Pod{}) // + Service, Secret, PVC
  • 不會觸發:只改 status(r.Status().Update)。metadata.generation 不會變,被 GenerationChangedPredicate 過濾掉。這是刻意的,否則 controller 自己寫 status 會一直觸發自己。
  • 會觸發:spec 改變,或這個 cluster 擁有的 Pod 被新增、更新、刪除。

套到 issue 的情境

  1. 流量下降時,autoscaler patch spec(降低 replicas、把名字加進 WorkersToDelete)。generation 改變,reconcile 立刻跑。
  2. 這次 reconcile 有跑,跑到 group A 建立失敗就 return,group B 的刪除沒有執行。

卡死從來不是通知的問題:reconcile 有被觸發、也有跑,只是在到 group B 之前就結束了。所以修法不需要新增任何觸發機制。

出錯時的 requeue

L403 回傳 ctrl.Result{RequeueAfter: DefaultRequeueDuration}, err。在 controller-runtime v0.25,err != nil 時 RequeueAfter 會被忽略(internal/controller/controller.go:494,還會記一行 warning),改走 AddRateLimited。預設 rate limiter 是每個 item 指數退避,約 5ms 起跳、加倍到上限 1000s,成功 reconcile 一次才會歸零。

所以 group A 一直被 quota 拒絕時,錯誤造成的重試會越來越稀疏,最久約 16 分鐘一次。但 watch event 還是會立刻處理,因為一般的 Add 不經過 rate limiter。

修好之後的流程

  1. autoscaler patch spec → reconcile → group A 建立失敗,記下錯誤、break → group B 刪掉 WorkersToDelete 的 Pod → 回傳錯誤。
  2. 這些刪除是擁有的 Pod 的 event,會觸發新一輪 reconcile,同時滿足 group B 的 delete expectation。
  3. 新一輪裡 group A 重試建立。這時 quota 有空位了,可以成功。

修好之後會自己恢復:group B 的刪除產生的 event,正好讓 group A 重試。

仍存在的缺口(不在範圍內):如果 quota 是因為這個 RayCluster 不擁有的東西而釋放(同 namespace 其他 workload 縮容,或 admin 調高 ResourceQuota),這個 cluster 收不到任何 event,group A 只能等退避計時器,最久約 1000s。這是現有的延遲問題,不屬於 #5364,在 PR 裡列為已知限制即可。

6. multi-host 是什麼

multi-host 的意思?

一個 worker replica 由多個 Pod 組成,每個 Pod 在不同機器上,而且只能一起運作。少任何一個,這個 replica 就沒用。

主要是為了 TPU。像 v4-16 這種 TPU slice 實體上分布在好幾台 VM(「host」),每台有一部分 chip。JAX/XLA 要所有 host 都在才能啟動,4 台裡有 3 台什麼也做不了。KubeRay 用 worker group 的 NumOfHosts 描述:

workerGroupSpecs:
- groupName: tpu-group
  replicas: 2       # 2 slices
  numOfHosts: 4     # each slice = 4 pods

總共 replicas × numOfHosts = 8 個 Pod,但 autoscaler 和 controller 把它當成 2 個單位,不是 8 個獨立 worker。

gate 開啟後的 label 和行為

ray.io/worker-group-replica-name:  tpu-group-abc12   # which slice
ray.io/worker-group-replica-index: 0                 # slice number
ray.io/replica-host-index:         2                 # host 2 of 4

有了這些 label,reconcileMultiHostWorkerGroup(L1286)可以整個 replica 一起管理:

  1. replica 裡任何一個 host 掛掉,整個 replica 刪掉,因為不完整的 slice 沒用。
  2. autoscaler 刪除 worker 時,刪掉那個 replica 的所有 host。
  3. 以完整 replica 為單位擴縮容:一次建立 NumOfHosts 個 Pod。

跟 #5364 的關係

quota 拒絕對 multi-host group 傷害更大。建立一個 replica 要連續 NumOfHosts 次建立,quota 可能放行 2 個、拒絕第 3 個,留下一個佔著 quota 卻什麼都不做的不完整 replica。下一輪規則 1 應該要把它刪掉,但如果排前面的 multi-host group 一直失敗,L1098 同樣的提早 return 會讓 controller 到不了後面 group 的清理。
