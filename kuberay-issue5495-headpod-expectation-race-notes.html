KubeRay issue #5495 · head pod reconciliation

Head Pod Expectation Race

整理自 2026-11-07 的問答(含與 Gemini 對話的校正) · issue #5495 · 重現 test epall:5495-head-pod-creation-race · branch fix/i-5495-headpod-expectation-race · 相關筆記:Issue 5364 Worker Group Deadlock、Pod Create vs Schedule

一句話:reconcilePods 先 List head pods(L1041),到 L1056 才呼叫 IsSatisfied。如果 informer 剛好在這兩次讀取之間收到上一輪建立的 head A,expectation 就會判定為滿足,但 controller 手上拿的還是先前那份空的清單,於是又建了一個 head B。

  • 不是 cache 壞了:informer 的最終一致性完全照設計運作,錯的是讀取順序。
  • 修法:先 IsSatisfied,通過才 List。worker 路徑(L1125 → L1134)本來就是這個順序,只有 head 路徑寫反了。
  • 測試:epall 的 compare branch 只有 test,沒有 fix 的 diff。issue 裡回報:現行順序 10/10 失敗,調換順序後 10/10 通過。

1. 現場發生了什麼

KubeRay v1.6.2、GKE 1.32。同一個 RayCluster 在 270ms 內被建了兩個 head,兩次 create request body 完全相同(都用 generateName)、來自同一個 operator Pod,但是由兩個不同的 reconcile ID 發出。

UTC 時間事件
22:32:51.650Reconcile A:找到 0 個 head,建立 head
22:32:51.748Reconcile A:建立 ...-c8nnt
22:32:51.884Reconcile A:status 計算時仍看到 0 個 head(HeadPodNotFound)
22:32:51.921Reconcile B:找到 0 個 head,建立 head
22:32:52.016Reconcile B:建立 ...-lfbq7
22:32:52.018Reconcile B:看到原本的 ...-c8nnt 為 Pending
22:32:52.034Reconcile B:status update conflict(發生在兩次 create 之後,不是成因)

影響:兩個 head 被排到不同 node。head service 是 headless,設了 publishNotReadyAddresses: true,selector 同時選到兩個 head,同一個 service 名稱後面掛著兩個獨立的 GCS。

相關 issue:#5336(Guarantee at most one serving head Pod,範圍較廣、被歸為 feature)、#3013(Make head Pod name deterministic)。

2. 交錯時序

需要兩個 reconcile 同時跑嗎?

不需要。controller-runtime 對同一個 key 不會同時跑兩個 reconcile。A 和 B 是先後執行的,真正在競爭的是 reconcile goroutine 和 informer goroutine:informer 在 B 的兩次讀取之間更新了 cache。

Reconcile A
API Server 建立 head A 成功,ExpectScalePod(head A, Create) 記下一筆 expectation
Reconcile B
r.List(&headPods):head A 還沒進 informer cache → 空清單
(若啟用 batch scheduler,DoBatchSchedulingOnSubmission 會打 API,空檔變更長)
↓ informer 在這段空檔收到 head A 的 watch 事件,寫入 cache
IsSatisfied → cached Get(head A) 找到 → 刪掉 expectation、回傳 true
拿第一步那份空清單判斷 len(headPods.Items) == 0 → 建立 head B

3. 兩種 cache:informer cache 和 itemsCache

k8s.io/client-go/tools/cache 就是 informer cache 嗎?

不完全是。這個套件同時包含 informer 的底層元件(Reflector、DeltaFIFO、Indexer)和通用的記憶體 store。scale_expectations.go 用的只是其中的 cache.NewIndexer,沒有 watch。

名稱存什麼誰更新跟 API Server 同步?
informer cache叢集裡的 Pod 物件,r.Get / r.List 讀它Reflector 透過 List/Watch 非同步寫入是(最終一致)
itemsCache(cache.Indexer)「我剛建/刪了某個 Pod」的 rayPod 紀錄程式碼手動:ExpectScalePod 加入、IsSatisfied 刪除否

Pod 的讀取確實走 cache:main.go:282-290 只對 Pod 設了 label selector(ByObject),沒有 DisableFor。

4. Expectation 在做什麼

為什麼需要 expectation?

對抗 cache lag。上一輪剛建好 Pod,watch 事件還在路上,下一輪 List 看不到就會再建一次。expectation 是一本本地帳:建立/刪除成功後記一筆,下一輪先問「記帳的那個 Pod,cache 看得到了嗎?」看不到就跳過這個 group 的 scale 決策。KubeRay 在 PR #2150(2024-11 合併)加入。

ray-operator/controllers/ray/expectations/scale_expectations.go:73

func (r *rayClusterScaleExpectationImpl) isPodScaled(ctx context.Context, rp *rayPod) bool {
    pod := &corev1.Pod{}
    switch rp.action {
    case Create:
        if err := r.Get(ctx, ..., pod); err == nil {   // cached Get
            return true
        }
        return rp.recordTimestamp.Add(ExpectationsTimeout).Before(time.Now())  // 30s 逾時
    case Delete:
        if err := r.Get(ctx, ..., pod); err != nil {
            return errors.IsNotFound(err)
        }
    }
    return false
}

IsSatisfied 逐筆呼叫 isPodScaled,滿足的就從 itemsCache 刪掉;任一筆不滿足就回傳 false。30 秒逾時是為了避免 Pod 剛建立就被別人刪掉時,expectation 永遠等不到。

跟 Kubernetes 上游的差別?

上游的 ControllerExpectations 用計數(adds/dels),由 informer event handler 遞減;KubeRay 改成追蹤具體 Pod 名稱,在 IsSatisfied 裡主動 Get。上游 syncReplicaSet 也是先 SatisfiedExpectations、再 podLister.List,跟這次要改的順序一樣。

Gemini 說 SatisfiedExpectations 在 manageReplicas() 裡呼叫,不對,是在 syncReplicaSet。

5. 重現 test 怎麼讀

為什麼在 Get interceptor 裡呼叫 c.Create?看起來很怪。

這是時序注入。fake client 沒有 API Server 也沒有 watch,所有物件都放在同一個記憶體 tracker 裡,所以「寫進 fake client」就等於「informer cache 已經收到」。controller 在 List 之後的下一個 Pod Get,正好是 IsSatisfied 裡那次,把它當觸發點就能精準卡進那段空檔:

Get: func(ctx, c, key, obj, opts...) error {
    if _, ok := obj.(*corev1.Pod); ok && key == client.ObjectKeyFromObject(&firstHead) && !cacheUpdated {
        // 模擬 informer 在 List 之後、Get 之前收到 head A
        require.NoError(t, c.Create(ctx, &firstHead))
        cacheUpdated = true
    }
    return c.Get(ctx, key, obj, opts...)
},
  1. reconcilePods 呼叫 List:firstHead 不在 store → 空清單。
  2. IsSatisfied 呼叫 Get(firstHead):interceptor 先把 firstHead 塞進 store,再 Get → 找到 → 滿足。
  3. controller 用空清單判斷 → 建 head B。Create interceptor 數到 headCreateAttempts == 1,assert 失敗。

cacheUpdated 確保只注入一次。不需要 sleep 或 goroutine,單執行緒就能 100% 重現。

其他寫法?

可以在 Get 裡直接把 firstHead 填進 obj 回傳,不動 store。但這樣最後 List 驗證剩下幾個 head 時,firstHead 不在 store 裡,assert 要另外處理。原作者的寫法比較短,也讓 store 的最終狀態保持完整。

6. 修法,以及為什麼調換順序就夠

把 head 的 List 移到 IsSatisfied 通過之後。batch scheduler 那段保持在 head reconcile 之前。

List 要放進 satisfied 分支裡面,不只是往下移幾行。沒滿足時本來就要跳過 head,清單用不到,不必多讀一次 cache。改完之後跟 worker 路徑同一個結構:

// Reconcile head Pod
if !r.rayClusterScaleExpectation.IsSatisfied(ctx, instance.Namespace, instance.Name, expectations.HeadGroup) {
    logger.Info("reconcilePods", "Expectation", "NotSatisfiedHeadExpectations, reconcile head later")
} else {
    headPods := corev1.PodList{}
    if err := r.List(ctx, &headPods, common.RayClusterHeadPodsAssociationOptions(instance).ToListOptions()...); err != nil {
        return err
    }
    switch {
    case len(headPods.Items) == 1: ...
    case len(headPods.Items) == 0: ... // create
    default: ...                        // >1, error
    }
}

DoBatchSchedulingOnSubmission(L1046-1054)跟 head 清單無關,留在原位,行為不變。

為什麼先檢查再 List 就保證看得到 head A?

Get 和 List 讀的是同一個 informer store。只要 Get 看到了 head A,後面的 List 一定也看得到,除非它真的被刪了。如果 expectation 還沒滿足,就跳過 head,根本不會用到清單。

還有沒有漏洞?

  • 30 秒逾時:逾時後 expectation 會判定為滿足,但 Pod 可能還沒進 cache。要 informer 延遲超過 30 秒才會發生,而且這是原本設計就接受的取捨。
  • Delete 方向:List 還看得到舊 head,Get 卻回 NotFound,判定為滿足。這時走的是 len==1 分支,用的是過期的 head 物件,後果比重複建立輕得多。調換順序後也一併修好。

不滿足時並不是「結束本輪 reconcile」(Gemini 的說法),而是只 log、跳過 head,然後繼續跑 worker groups(L1124)。

8. IsSatisfied 逐步拆解

IsSatisfied 回答的是「這個 group 之前記下的 Pod 建立/刪除,informer cache 是不是都看得到了」。它讀的是 cache,不是 API Server。

帳本:itemsCache

controller 每次建立或刪除 Pod 成功,就呼叫 ExpectScalePod 記一筆(scale_expectations.go:56),內容是 name、namespace、group、rayCluster、action(Create / Delete)和 recordTimestamp。

鍵格式用途
主鍵 Key()ns/podName一個 Pod 只會有一筆紀錄
GroupIndexns/cluster/groupIsSatisfied 用它撈出某個 group 的所有紀錄
RayClusterIndexns/clusterRayCluster 被刪除時,Delete() 一次清掉整個 cluster 的紀錄

head 也算一個 group,名稱是 expectations.HeadGroup。

流程(:93)

items := r.itemsCache.ByIndex(GroupIndex, "ns/cluster/group")  // ① 撈出這個 group 的所有紀錄
for i := range items {
    rp := items[i].(*rayPod)
    if !r.isPodScaled(ctx, rp) {     // ② 逐筆用 cached Get 檢查
        return false                 // ③ 有一筆沒滿足就立刻回 false
    }
    r.itemsCache.Delete(items[i])    // ④ 滿足的那筆從帳本刪掉
}
return true                          // ⑤ 全部滿足,或本來就沒有紀錄
action怎樣算滿足逾時
Createcached Get 找得到這個 Pod有。記錄超過 30 秒(ExpectationsTimeout)也算滿足
Deletecached Get 回傳 NotFound沒有。cache 一直看得到 Pod,就一直不滿足

容易被誤會的地方

  1. 名字像查詢,其實有副作用。滿足的紀錄會被刪掉(④)。在 #5495 裡,Reconcile B 的 IsSatisfied 看到 head A 之後,head A 的紀錄就消失了。B 接著拿舊的空清單建了 head B,下一輪也沒有紀錄可以擋住它。
  2. 刪除是逐筆的。3 筆紀錄中第 1 筆滿足、第 2 筆沒滿足:第 1 筆已被刪,函式在第 2 筆回 false,第 3 筆沒被檢查。下一輪從剩下的第 2、3 筆接著檢查。
  3. 沒有紀錄就是 true。第一次 reconcile 或 operator 剛重啟時帳本是空的,直接放行。帳本只在記憶體裡,重啟就沒了,這層保護在重啟後暫時是空的。
  4. 只回答「cache 是否追上我自己做過的事」,不回答「Pod 數量對不對」。數量要靠後面的 List。#5495 的問題就是兩次讀取中間 cache 更新了,閘門和清單看到的是不同時間點的 cache。

一句話:IsSatisfied 是一道閘門,「我做過的事 cache 都看到了」才放行,並且順手把已經看到的紀錄劃掉。所以要先過閘門再 List,清單才保證至少和閘門看到的一樣新。

9. reconcile ID 去哪查

reconcile ID 是 controller-runtime 產生的,KubeRay 沒有自己定義。每輪 reconcile 開始時產生一個 UUID,掛到 logger 上,也放進 ctx:

controller-runtime@v0.25.0/pkg/internal/controller/controller.go:472

reconcileID := uuid.NewUUID()
log = log.WithValues("reconcileID", reconcileID)
ctx = addReconcileID(ctx, reconcileID)

KubeRay 用 ctrl.LoggerFrom(ctx) 取 logger(例如 raycluster_controller.go:116),同一輪的每一行 log 都自動帶這個欄位。operator stdout 預設是 JSON(main.go:107,--log-stdout-encoder=json)。

# kubectl
kubectl -n <ns> logs deploy/kuberay-operator --since=1h \
  | jq -c 'select(.RayCluster.name=="<cluster>") | {ts, reconcileID, msg}'

# GKE Cloud Logging
resource.type="k8s_container"
resource.labels.container_name="kuberay-operator"
jsonPayload.reconcileID="<id>"

程式裡要拿到 ID,用 controller.ReconcileIDFromContext(ctx)(同檔 :530)。

issue 裡的 Reconcile A / B 就是依 reconcileID 分組,再對照 audit log 兩次 create 的時間戳。兩組 log 來自同一個 operator Pod、ID 不同、時間先後錯開,所以能判斷是同一個 operator 依序跑了兩輪,而不是兩個 replica 同時在跑。
