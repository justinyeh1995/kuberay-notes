Node Label Delivery

整理自 2026-10-09 的問答 · 相關筆記:Pod Create vs Schedule

一句話:這系列 PR 讓 Ray worker 在 ray start 時就拿到它所在 K8s Node 的 label(zone、nvidia.com/gpu.clique 等)。這是在 KubeRay 上做 Topology-Aware Scheduling(TAS)的基礎。

  • 使用者在 workerGroupSpecs[].labelRefs 宣告要哪些 node label。
  • 兩個 mutating webhook 合作:pod 建立時先準備好接收的 env,pod bind 時才把 node label 寫進 annotation。
  • 由 NodeLabelDelivery feature gate 控制(alpha,預設關閉),需要 ENABLE_WEBHOOKS=true 和 Ray ≥ 2.45。

1. 為什麼重要

核心難題:node 資訊要等排程完才知道,但 ray start 的參數在 pod 建立時就決定了。

  • Ray 排程需要知道機器的位置和硬體拓撲。例如讓 collective 通訊留在同一個 GPU NVLink clique,或讓 placement group 留在同一個 zone。
  • 這些資訊只在 K8s Node label 上,Ray worker 看不到。
  • workerGroupSpecs[].labels 只能放靜態值。建 pod 時還不知道它會被排到哪個 node。
  • scheduler bind 完才知道 node,這時 pod spec 已經不能改了(見 Pod Create vs Schedule 的兩個階段)。

使用者介面

workerGroupSpecs:
- groupName: gpu
  labelRefs:
  - name: ray.io/zone
    valueFrom:
      nodeRef:
        fieldPath: metadata.labels['topology.kubernetes.io/zone']
  - valueFrom:
      nodeRef:
        fieldPath: metadata.labels['nvidia.com/gpu.clique']  # name 預設等於 node label key

3. 機制:兩段式 webhook

一個 worker pod 從建立到 ray start

  1. RayCluster controller 建立 worker pod

    container args 帶 KubeRay 產生的 ray start(KUBERAY_GEN_RAY_START_CMD)

  2. Pod CREATE webhook(Fail)

    加 env RAY_NODE_LABELS_JSON,用 downward API 指向 annotation ray.io/node-labels;改寫 ray start,先寫檔再加 --labels-file

  3. Scheduler 建立 pods/binding

    這時才決定 pod 落在哪個 node

  4. pods/binding webhook(Ignore,5s)

    讀 Node labels → 套 labelRefs 和 allowedNodeLabels 白名單 → JSON 寫進 Binding annotation

    缺 label 或不在白名單
    發 Warning event RequiredNodeLabelMissing,binding 照常放行,但不寫 annotation

  5. API server 套用 binding

    spec.nodeName 和 annotation 一起寫到 pod

  6. 容器啟動,downward API 解析 env

    寫入 /tmp/ray-labels.yaml → ray start --labels-file

    沒有 annotation 時
    env 是空的 → 印出錯誤後 exit 1,ray 不啟動

關鍵在時序:env 在步驟 2 就加好了,但 downward API 要到容器啟動(步驟 6)才解析,所以拿得到步驟 4 才寫進去的 annotation。

前置條件與防呆

  • ValidateRayClusterSpec:有 labelRefs 時要求 feature gate 已開啟、ENABLE_WEBHOOKS=true、Ray ≥ 2.45(--labels-file 從這版開始才有)。
  • utils.NodeLabelKey:fieldPath 只接受 metadata.labels['<key>']。
  • RBAC 多了 nodes get;Helm 加了 cert、issuer、mutating webhook 範本。

4. 設計重點(review 時要看的地方)

重點做法理由
失敗策略不對稱Pod webhook Fail;binding webhook Ignore + 5s timeout建立 pod 時可以直接擋下;binding 失敗不能卡住 scheduler,所以讓錯誤在容器啟動時才出現
白名單operator 設定 allowedNodeLabels避免使用者讀取任意 node label
binding 的熱路徑先用 pod 名稱前綴 <cluster>-<group>-worker- 比對 cache 中的 RayCluster所有 pod 的 binding 都會進來,要能很快放行無關的 pod;前綴可能重複,最後還是以 pod labels 判斷 group
冪等env 已存在、或 annotation 已存在,就直接放行webhook 可能被重複呼叫(reinvocation)
依賴 KubeRay 產生的 ray start找不到 KUBERAY_GEN_RAY_START_CMD,或 args 不只一個元素,就拒絕建立 pod需要改寫 ray start;自訂啟動指令的使用者不能使用這個功能
