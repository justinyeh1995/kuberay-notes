一句話:KubeRay operator 只跟 kube-apiserver 說話。unit test 的 fakeClient 取代的就是「透過 client 看到的 apiserver」,不是 controller manager;而且 unit test 連 KubeRay 自己的 Manager 都沒有,直接把 reconcilePods 當普通函式呼叫一次。

  • kube-controller-manager:Kubernetes 內建的 controller(ResourceQuota、ReplicaSet…),KubeRay 從不直接跟它溝通。
  • KubeRay operator 本身也是一個「controller manager」:controller-runtime 的 Manager,裡面跑 RayClusterReconciler。
  • 三種測試層級的差別,就在於這些元件哪些是真的、哪些是假的或根本不存在。

1. 真實環境裡有哪些元件

KubeRay operator

一個 Pod · ray-operator/main.go

Manager · ctrl.NewManager(main.go:312)
informer cache · watch 物件,讀取走這裡
work queue · 排隊、退避、requeue
RayClusterReconciler · Reconcile → reconcilePods
HTTP⇄只跟 apiserver

Kubernetes

control plane + node

kube-apiserver · 唯一的入口;認證、授權、admission(含 ResourceQuota)、驗證
etcd · 存所有物件
kube-scheduler · 把 Pod 排到 node
kube-controller-manager · 內建 controller:resourcequota(算 status.used)、replicaset、deployment…
kubelet(每台 node)· 真的把 container 跑起來

所有元件都只透過 kube-apiserver 溝通,彼此不直接說話。KubeRay 也一樣。

「controller manager」到底指誰?

這個詞有兩個意思,這就是容易搞混的地方:

說法指的是跑什麼
kube-controller-managerKubernetes 自帶的一個程式內建 controller:ResourceQuota、ReplicaSet、Deployment、Namespace…
controller-runtime 的 Manager寫 operator 用的 Go 函式庫裡的型別你自己寫的 reconciler,例如 KubeRay 的 RayClusterReconciler、RayJobReconciler

兩者是同一種模式(watch 物件 → 比對期望與現況 → 補差距),只是一個管 Kubernetes 內建資源,一個管 KubeRay 的 CRD。KubeRay operator 可以想成「專門管 RayCluster 的 controller manager」,跟 kube-controller-manager 是平行的,都只是 apiserver 的客戶端。

KubeRay 的 Manager 做了什麼?

  • main.go:312 ctrl.NewManager(...) 建出 Manager。
  • main.go:355 起 SetupWithManager(mgr, ...) 把各個 reconciler 註冊進去,宣告要 watch 什麼(For(&RayCluster{})、Owns(&Pod{})…)。
  • Manager 負責:建 informer cache、收 watch event、把 request 放進 work queue、出錯時退避重試,最後呼叫 Reconcile(raycluster_controller.go:114)。
  • reconciler 裡的 r.Client:讀取(Get/List)預設走 informer cache,寫入(Create/Update/Delete)直接打 apiserver。

3. 測試裡常見的基本型別

runtime.Object 是什麼?WithRuntimeObjects 做什麼?

runtime.Object 是 Kubernetes Go 函式庫裡的一個 interface,所有 API 型別(Pod、Service、RayCluster…)都實作它:

// k8s.io/apimachinery/pkg/runtime
type Object interface {
    GetObjectKind() schema.ObjectKind   // 我是哪種 Kind
    DeepCopyObject() Object             // 複製一份自己
}

「runtime objects」就是「任何 Kubernetes 物件」的通稱。用 interface 的好處是一個 slice 可以裝不同種類的物件,例如 testPods = []runtime.Object{&corev1.Pod{...}, ...}(raycluster_controller_unit_test.go:105)。

WithRuntimeObjects(testPods...):fake client 建好時,記憶體裡就已經有這些物件,像 cluster 裡本來就存在它們。它們是直接放進去的,不經過 interceptor 的 Create,所以不會被拒絕。

Scheme 是什麼?

一張對照表:Go 型別 ↔ Kubernetes 的 GroupVersionKind(GVK)。client 拿到一個 Go struct,要靠 scheme 才知道它是什麼 Kind、打 apiserver 的哪個 URL、怎麼序列化。

Go 型別GVK
corev1.Pod/v1, Kind=Pod(core group)
rayv1.RayClusterray.io/v1, Kind=RayCluster

內建型別預設已註冊;CRD 要自己註冊:

newScheme := runtime.NewScheme()      // 一張空表
_ = rayv1.AddToScheme(newScheme)      // 加入 RayCluster、RayJob…
_ = corev1.AddToScheme(newScheme)     // 加入 Pod、Service…
  • 其他測試(例如 L1102–1104)建 newScheme 再 .WithScheme(newScheme) 給 fake client,因為它們要存 RayCluster 這種 CRD。
  • #5364 的測試沒有 .WithScheme(...),fake client 用預設 scheme。裡面有 Pod,夠用,因為只存 Pod。所以註解寫「with newScheme」是不準確的。
  • reconciler 的 Scheme: scheme.Scheme:buildWorkerPod 用它設定 owner reference(raycluster_controller.go:1802 的 SetControllerReference(&instance, &pod, r.Scheme)),要從 scheme 查出 RayCluster 的 GVK。失敗時只記 log(L1803),Pod 照樣 build,不影響這個測試。

RayClusterGroupPodsAssociationOptions 是什麼?

回傳「怎麼找出某個 RayCluster 某個 group 的 Pod」的查詢條件(common/association.go:113):

func RayClusterGroupPodsAssociationOptions(instance *rayv1.RayCluster, group string) AssociationOptions {
    return AssociationOptions{
        client.InNamespace(instance.Namespace),          // 同一個 namespace
        client.MatchingLabels{
            utils.RayClusterLabelKey:   instance.Name,    // ray.io/cluster=<cluster 名稱>
            utils.RayNodeGroupLabelKey: group,            // ray.io/group=<group 名稱>
        },
    }
}

AssociationOptions 是 client.ListOption 的 slice,.ToListOptions() 展開成 r.List(...) 的參數。

  • controller(raycluster_controller.go:1079):每個 group 一開始用它列出自己的 Pod。
  • 這也是 group B 必須沿用 small-group 的原因:fixture 的 pod1–pod5 標的是 ray.io/group=small-group,換名字 controller 就找不到它們。

測試裡也要用 RayClusterGroupPodsAssociationOptions 列 Pod 嗎?

不用。raycluster_controller_unit_test.go 的慣例是用 setupTest 建好的 workerSelector(L417,條件是 ray.io/cluster=raycluster-sample + ray.io/group=small-group):

寫法次數用途
&client.ListOptions{LabelSelector: workerSelector, Namespace: namespaceStr}13列 fixture 那個 worker group(small-group)的 Pod
client.InNamespace(namespaceStr)18列 namespace 裡全部的 Pod(含 head)
common.RayClusterGroupPodsAssociationOptions(...)0(#5364 一開始用過,已換掉)controller 自己的查詢條件

#5364 一開始用 controller 的函式,是為了保證測試檢查的就是 controller 認為的那批 Pod。但檔案慣例很明確,group B 剛好就是 small-group,開頭的 assert 也守著 fixture 前提,所以換成 workerSelector:

err = fakeClient.List(ctx, &podList, &client.ListOptions{
    LabelSelector: workerSelector,
    Namespace:     namespaceStr,
})

為什麼 workerSelector 列出來的就是 group B?

因為它用 group 名稱的 label 篩選,而 group B 的名字剛好就是 small-group。

1. workerSelector 篩的是 small-group(setupTest,L398–417):

instanceReqValue := []string{instanceName}      // "raycluster-sample"
instanceReq, _ := labels.NewRequirement(utils.RayClusterLabelKey,   selection.Equals, instanceReqValue)
groupNameReqValue := []string{groupNameStr}     // "small-group"
groupNameReq, _ := labels.NewRequirement(utils.RayNodeGroupLabelKey, selection.Equals, groupNameReqValue)

workerSelector = labels.NewSelector().Add(*instanceReq).Add(*groupNameReq)
// ray.io/cluster = raycluster-sample  AND  ray.io/group = small-group

2. group B 就是 small-group:groupB := testRayCluster.Spec.WorkerGroupSpecs[0],fixture 唯一的 group,沒有改名;只有 group A 被改成 group-a。

3. 每個 Pod 的 label 決定會不會被篩到:

Podray.io/group符合 workerSelector?
headNodehead-group✗
pod1–pod5(fixture)small-group✓
group A 的 Podgroup-a✗(而且建立一律失敗,根本不存在)

前提有兩個:group B 沿用 small-group(改名就找不到 Pod)、fixture 的 Pod 標的是 small-group(utils.RayNodeGroupLabelKey: groupNameStr,L145 等處)。開頭的三行 assert(fixture 只有一個 group、6 個 Pod)守住這些前提,fixture 一變就先在那裡失敗。

workerSelector 這個名字容易讓人以為是「所有 worker」,其實只篩 small-group 一個 group。可以在斷言前補一句註解,例如 // workerSelector selects small-group, which is group B.

4. interceptor 回傳什麼錯誤、要斷言什麼

為什麼不直接回傳 utils.ErrFailedCreateWorkerPod?

這個標記是 controller 自己包上去的(L1421 errstd.Join(utils.ErrFailedCreateWorkerPod, err)),L1099 再靠 errstd.Is 認它。fake 若先給了標記,就測不到「controller 有沒有包」:

fake Create 回傳L1421 忘了包標記時測試
不帶標記的錯誤(errors.New("exceeded quota"))沒有標記 → L1099 return → group-b 沒被刪失敗,抓到 bug
utils.ErrFailedCreateWorkerPod本來就有標記 → L1099 繼續 → group-b 被刪通過,bug 被藏起來

TestEvents_FailedPodCreation 可以回傳標記,是因為它只檢查 event(L1703 拿到錯誤就發),跟錯誤內容無關。

NewForbidden 還是 errors.New?

repo 裡 interceptor 共 9 處,大多回傳簡單錯誤(rayjob_controller_unit_test.go 的 errors.New("random")、errInjected)。只有一開始的 #5364 版本用 k8serrors.NewForbidden(...),風格不一致,所以改成 errors.New("exceeded quota")。重點是「不帶標記」,不是「一定要像 apiserver」。

break 改成 continue 也會過?

會。continue 只是多試幾次,最後一樣離開內層迴圈、跑到 group-b。測試裡每次 Create 都失敗,所以 group-a 也沒有多建出 Pod:

breakcontinue
Create 被呼叫幾次(diff=2)12
errs 裡幾個錯誤12
group-a 實際建出的 Pod00
ErrorIs、group-b 剩 pod1, pod2, pod5通過通過

原本用 createAttempts == 1 分辨兩者(它抓到過第一次 L1202 寫成 continue 的版本)。後來判斷價值不高,拿掉了。代價:continue 不會再被測試擋下;reviewer 問到時再說明。

5. 怎麼選測試層級

想驗證的是用例子
reconciler 拿到某個輸入/錯誤後怎麼做unit test#5364:建立失敗後有沒有繼續處理 group-b
跟 apiserver 互動的細節(CRD schema、patch、status 更新、watch 觸發)envtestspec 改了有沒有觸發 reconcile、status 有沒有寫進去
需要真的排程、真的 container、真的內建 controllere2eRay job 真的跑完、quota 真的擋下建立

原則:用能涵蓋這個行為的最低層級。越低越快、越穩定、越好除錯;越高越接近真實,但慢、容易 flaky。
